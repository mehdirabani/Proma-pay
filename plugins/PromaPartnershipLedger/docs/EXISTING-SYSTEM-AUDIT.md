# ممیزی سامانهٔ فعلی پیش از جایگزینی

تاریخ بررسی: ۲۰۲۶-۱۰-۲۱
مبنای بررسی: سورس Workspace در commit `9752038`، نسخهٔ هستهٔ Proma Pay `7.0.3`، manifest افزونهٔ `proma-inventory-partners` نسخهٔ `1.1.2` و مستندات/آزمون‌های موجود در مخزن.

## دامنه و محدودیت شواهد

این ممیزی سورس و schema افزونه را بررسی می‌کند. در این مرحله به دیتابیس نصب‌شده، وضعیت فعال/غیرفعال افزونه در Plugin Registry یا داده‌های واقعی انبار دسترسی و تأیید نگرفته‌ایم؛ بنابراین هیچ آمار زنده، نتیجهٔ مهاجرت، یا وضعیت عملیاتی ادعا نمی‌شود. گزارش آزمون افزونهٔ قدیمی در مخزن مورخ ۲۰۲۶-۱۰-۱۳ است و نتایجش به همان fixture و محیط گزارش‌شده محدود است.

## معماری هسته و افزونه

- Proma Pay یک برنامهٔ PHP با MVC اختصاصی است، نه WordPress. افزونه‌ها با `plugin.json`، `PluginServiceProviderInterface`، Plugin Manager، route/permission ثبت‌شده و SQL migration بارگذاری می‌شوند.
- هسته route، migration، مجوز، lifecycle و hook افزونه را فراهم می‌کند. API مناسب برای توسعهٔ افزونه بدون کپی هسته وجود دارد.
- `PromaInventoryPartners` در manifest به core `>=6.0.2` و PHP `>=8.1` نیاز دارد و وابستگی رسمی به افزونهٔ دیگری اعلام نکرده است.
- افزونهٔ فعلی جداول اختصاصی `plugin_inventory_*` دارد. کالا، محموله، سریال/IMEI، حرکت موجودی، خرید، فروش، آورده، دفترکل، هزینه و تسویه در همین schema نگهداری می‌شوند.
- جداول اصلی core مانند قرارداد، قسط و پرداخت مرجع قرارداد و وصول مشتری باقی می‌مانند؛ افزونه آن‌ها را به‌عنوان جداول موجودی بازسازی نمی‌کند.

## موتور قیمت‌گذاری و اقساط

کد فعلی فروش اقساطی را به قرارداد موجود وصل می‌کند و وصول را از رویداد پرداخت به فروش نسبت می‌دهد. گزارش سازگاری قبلی می‌گوید مبلغ اصل قرارداد در مدل core تومان است و تخصیص اصل در رکورد پرداخت انجام می‌شود. فرمول‌های نرخ ماهانه، ساده/مرکب، مبنای «کل قیمت پایه» در برابر «مبلغ تأمین‌شده»، Snapshot سیاست و تخصیص مستقل سود مدت بازپرداخت در افزونهٔ موجود مستند یا پیاده نشده‌اند.

بنابراین پیش از اتصال موتور قیمت‌گذاری جدید به فرم/محاسبهٔ قرارداد core، باید جریان واقعی ایجاد قرارداد و پیش‌پرداخت در staging آزموده شود. در این تغییر، قراردادهای core و مبالغ تاریخی آن‌ها بازنویسی نمی‌شوند و تغییر حداقلی core نیز تا اثبات نیاز انجام نمی‌شود.

## نتیجهٔ معماری

1. افزونهٔ جدید باید ادامه‌دهندهٔ همان داده‌های `plugin_inventory_*` باشد؛ ساخت جداول موازی کالا، محموله، فروش، پرداخت یا journal ممنوع است.
2. جداول تازه فقط برای قابلیت‌های واقعاً جدید مانند قرارداد مشارکت، نسخهٔ سیاست و Snapshot قواعد قابل افزودن‌اند و باید به شناسه‌های مرجع قدیمی متصل شوند.
3. در cutover فقط یک provider باید routeها و hookهای موجودی/فروش را ثبت کند. فعال‌بودن هم‌زمان دو provider می‌تواند event را دوبار پردازش کند و باید با guard lifecycle مسدود شود.
4. تغییر core برای انتقال داده لازم نیست. hook اصلاح پرداخت و دسترسی مشارکت‌محور کمبودهای هسته‌ای هستند؛ تا زمانی که راه افزونه‌ای امن اثبات نشده، این کمبودها باید در برنامهٔ تکمیلی/تطبیق دستی باقی بمانند.
5. جایگزینی عملیاتی، آمادگی Production یا موفقیت Migration فقط پس از اجرای تطبیق روی دیتابیس staging/واقعی و تکمیل ماتریس پذیرش قابل اعلام است.
