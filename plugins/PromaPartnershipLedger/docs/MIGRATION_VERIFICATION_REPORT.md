## وضعیت runtime هنگام آزمون

در اولین مشاهدهٔ Plugin Manager در این نوبت، successor از قبل فعال بود. رکورد افزونهٔ قدیمی در `system_plugins` وضعیت `removed` و زمان `deleted_at=2026-10-22 01:48:13` داشت و پوشهٔ آن در `C:\laragon\www\proma\plugins` وجود نداشت. این نوبت هیچ تغییر lifecycle، غیرفعال‌سازی، حذف فایل یا فعال‌سازی انجام نداد.

Plugin Registry برای هر سه migration successor status=success دارد: `2026_10_13_inventory_partners_core.sql`، `2026_10_13_inventory_partners_v110.sql` و `2026_10_21_partnership_ledger.sql`. بنابراین در runtime محلی یک provider فعال است و مسیرهای successor پاسخ می‌دهند. guardهای دو provider به‌صورت ایزوله با stub آزموده شدند؛ آزمون lifecycle واقعی با هر دو provider حاضر ممکن نشد، چون legacy در runtime نصب نیست.

## دامنه و روش تطبیق

وضعیت عملیاتی با queryهای فقط‌خواندنی پیش و پس از آزمون رابط گرفته شد. backup پیش از migration افزایشی در `C:\laragon\backup\mysql\proma_test-before-ledger-2026-10-21.sql` موجود است. successor همان جداول `plugin_inventory_*` را مصرف می‌کند؛ دادهٔ موجودی و دفترکل کپی یا import نمی‌شود. migration اختصاصی successor جدول نسخه‌های قواعد مالی را اضافه می‌کند.

## نتیجهٔ Migration و rollback

- در `proma_test` دادهٔ عملیاتی موجودی/شراکت برای انتقال وجود ندارد؛ یک انبار مشترک حفظ شده و دادهٔ موازی ساخته نشده است.
- migrationهای قدیمی و successor هرکدام در Plugin Registry ثبت شده‌اند. migrationهای DDL از `CREATE TABLE IF NOT EXISTS` و تغییرات شرطی استفاده می‌کنند؛ queryهای پس از فعال‌شدن successor هیچ کالای تکراری یا سند مالی تازه‌ای پیدا نکردند.
- هنگام snapshot، successor تنها provider فعال بود و legacy از پوشهٔ runtime حذف شده بود. گزارش تطبیق پیش از ثبت این وضعیت به‌روز شده بود.
- بازگشت با یک کلیک اکنون ممکن نیست؛ ابتدا باید بسته/فایل‌های legacy به runtime بازگردند و سپس rollback روی همان نسخه بررسی شود. آزمون rollback انجام نشده است.

این گزارش cutover Production را تأیید نمی‌کند. دادهٔ فعلی خالی بودن تطبیق را آسان می‌کند، اما parity کامل، جریان‌های پرداخت و مالی، نقش‌ها و rollback هنوز روی staging اثبات نشده‌اند.
