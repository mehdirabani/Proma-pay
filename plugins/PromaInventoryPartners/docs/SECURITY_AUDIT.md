# گزارش بازبینی امنیتی

تاریخ: ۲۰۲۶-۱۰-۱۳

این سند بازبینی ایستای سورس افزونه و قرارداد core به‌علاوهٔ آزمون تراکنشی محدود روی MySQL 8.4 ایزوله را ثبت می‌کند. آزمون نفوذ، نقش‌های واقعی مرورگر و staging کامل اجرا نشده؛ این گزارش گواهی امنیت یا تأیید Production نیست.

## کنترل‌های مشاهده‌شده و آزموده‌شده

- routeهای manifest مجوز صریح دارند؛ routeهای نوشتن POST هستند.
- `onlyPost()` هسته متد HTTP و `Csrf::verify()` را کنترل می‌کند؛ فرم‌های UI فیلد CSRF دارند.
- queryهای service از placeholderهای `Model` استفاده می‌کنند؛ LIMITهای پویا عددی و محدود هستند.
- outputهای template با helper `e()` escape می‌شوند.
- API خواندنی همان مجوزهای route را می‌گیرد و هزینه/قیمت حساس به `view_costs` محدود است.
- CSV برای کاهش formula injection مقادیر شروع‌شونده با `=`, `+`, `-`, `@` را escape می‌کند.
- عملیات مالی حساس audit log دارند؛ اسناد ledger و stock حذف آبشاری ندارند.
- سند دفترکل، پرداخت، خرید، فروش، آورده، تعدیل و تسویه از کلیدهای یکتا/idempotency در سطوح مربوط استفاده می‌کنند.
- آزمون MySQL ایزوله، توازن اسناد، جلوگیری از فروش بیش از موجودی و رقابت دو فروش برای یک واحد را بررسی کرد؛ فقط رقابت فروش اجرا شد.
- ابزار Application Security Auditor Forge X با حالت `--capabilities` روی افزونه اجرا شد. خروجی PHP را با parser ساختاری و پوشش معنایی محدود تحلیل می‌کند؛ بنابراین `CANDIDATE` را یافتهٔ تأییدشده تلقی نکردم.
- دو نمونهٔ قابل‌بررسی از خروجی ابزار false positive بودند: برچسب SQL injection روی `Model::execute()` با placeholder و پارامترهای جداگانه قرار داشت؛ برچسب SSRF روی lookup دیتابیس بود و مسیر درخواست شبکه‌ای وجود نداشت. همهٔ candidateهای خروجی دستی triage نشده‌اند و به همین دلیل نتیجهٔ اسکن، گواهی نبود آسیب‌پذیری نیست.

## ریسک‌های باز

1. **یکپارچگی پرداخت:** event اصلاح/ابطال پرداخت در core موجود نبود؛ بعد از اصلاح، تطبیق دستی لازم است.
2. **استقرار:** migration روی MySQL 8.4 با fixture محدود موفق بود؛ schema کامل core، MySQL 5.7 و MariaDB آزمایش نشده‌اند.
3. **هم‌زمانی:** فروش آخرین واحد با دو process موفق بود؛ رقابت هم‌زمان تسویه/انتقال و بار سنگین آزمایش نشده‌اند.
4. **سطوح دسترسی:** denial واقعی، IDOR و افشای فیلدها با نقش‌های محدود از طریق HTTP/API آزمایش نشده‌اند.
5. **قواعد تجاری:** VAT، کارمزد، برگشت جزئی UI، بدهی تأمین‌کننده و accounting قانونی پوشش کامل ندارند؛ گزارش سود و زیان صورت قانونی نیست.
6. **تحلیل ایستا:** اسکن ساختاری چند candidate پرنویز تولید کرد؛ نمونه‌های بررسی‌شده false positive بودند، اما کل مجموعهٔ candidateها بازبینی نشده است. اجرای parser کامل PHP و triage مستقل در pipeline انتشار انجام نشده.

## توصیهٔ staging

مجوز `view_costs` و دسترسی دفترکل/تسویه را محدود کنید، رفتار CSRF و permission denial را با نقش‌های واقعی بیازمایید و ثبت سند/گردش را پس از هر عملیات با گزارش مستقل تطبیق دهید. نتیجهٔ این آزمون‌ها در این اجرا ثبت نشده است.
