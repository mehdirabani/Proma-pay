# معماری افزونه

## جایگاه در Proma Pay

Proma Pay این نصب یک برنامهٔ PHP با MVC اختصاصی و Plugin Manager است، نه WordPress. افزونه با شناسهٔ `proma-inventory-partners` از قراردادهای `PluginManifest` و `PluginServiceProviderInterface` استفاده می‌کند و مسیرهای UI را با کنترل دسترسی Plugin Manager ثبت می‌کند. فایل‌های افزونه در پوشهٔ خودش قرار دارند و هیچ فایل core برای این پیاده‌سازی تغییر داده نشده است.

## لایه‌ها

- `plugin.json`: نسخه، حداقل نسخهٔ core و PHP، مجوزها، مسیرها، migration و assetها.
- `src/InventoryPartnersServiceProvider.php`: بارگذاری کلاس‌ها، ثبت route و منو، seed اولیه، health check و اتصال به hookها.
- `src/Domain`: تبدیل پول و تعداد، تخصیص صحیح با بزرگ‌ترین باقیمانده و محاسبهٔ بهای تمام‌شده/سود.
- `src/Services`: عملیات تراکنشی خرید، فروش، مالکیت، گردش موجودی، دفترکل، شریک، تسویه و گزارش.
- `src/Controllers`: اتصال route به service، کنترل POST/CSRF، مجوزهای route و خروجی CSV/API.
- `views/page.php`, `assets/css`, `assets/js`: رابط RTL فارسی با الگوهای Proma Pay و کلاس‌های CSS با پیشوند `pip-`.
- `migrations`: جداول اختصاصی افزونه با پیشوند `plugin_inventory_`.

دسترسی داده از `Model` مرکزی Proma Pay و پرس‌وجوهای پارامتری استفاده می‌کند. موتور مالی به فرم‌ها وابسته نیست. serviceهای ثبت سند در تراکنش جاری شرکت می‌کنند؛ اگر تراکنشی فعال نباشد، خودشان تراکنش را آغاز و پایان می‌دهند.

## جریان‌های مهم

### خرید و موجودی

خرید تک‌کالایی در یک تراکنش، سربرگ خرید، محموله، سهم مالکیت سرمایه و سود، واحدهای سریالی، گردش ورود و سند دفترکل را می‌سازد. هزینهٔ قابل انتساب میان تعداد تقسیم می‌شود و باقیماندهٔ ریالی در خود محموله نگهداری می‌شود تا خروج‌های بعدی هزینه را دقیقاً مصرف کنند. تغییر مستقیم ماندهٔ انبار از UI ارائه نشده است.

### فروش و تخصیص وجه

فروش از محمولهٔ انتخاب‌شده انجام می‌شود. service محموله را قفل می‌کند، موجودی و سریال را بررسی می‌کند، مالکیت و نرخ‌های مالی را به snapshot فروش منتقل می‌کند، گردش خروج و اسناد مالی را می‌نویسد. وجه دریافتی ابتدا ماندهٔ اصل سرمایهٔ شرکا را کاهش می‌دهد؛ فقط پس از آن سود وصول‌شده در حساب قابل پرداخت قرار می‌گیرد. فروش قراردادی به یک قرارداد متصل می‌شود و برای هر قرارداد حداکثر یک فروش افزونه ثبت می‌شود.

### دفترکل و تسویه

سند دفترکل با کلید رویداد یکتا، hash درخواست و توازن بدهکار/بستانکار ثبت می‌شود؛ سند موجود با همان کلید و محتوای متفاوت پذیرفته نمی‌شود. اصلاح با سند معکوس ثبت می‌شود. درخواست‌های تسویهٔ باز، ماندهٔ قابل درخواست شرکا را رزرو می‌کنند و هنگام تأیید و پرداخت دوباره مانده کنترل می‌شود.

### اتصال به قرارداد و پرداخت

hookهای موجود در core برای `payment.completed` و `contract.cancelled` استفاده می‌شوند. پرداخت‌های قطعی با شناسهٔ پرداخت و کلید idempotency تخصیص می‌یابند. در کد core بررسی‌شده hook عمومی اصلاح/ابطال پرداخت وجود نداشت؛ بعد از اصلاح پرداخت باید صفحهٔ فروش را با مجوز مدیریت فروش دستی تطبیق داد.

## تغییرناپذیری و حذف

اسناد قطعی مالی و گردش‌ها حذف آبشاری نمی‌شوند. provider در حذف یا غیرفعال‌سازی داده را پاک نمی‌کند. نرخ‌های جاری محصول و سهم پیش‌فرض شریک روی snapshotهای تاریخی خرید و فروش اثر نمی‌گذارند.

## محدودهٔ این نسخه

نسخهٔ اول به خرید و فروش تک‌ردیفی، مرجوعی کامل، یک سطح موجودی Lot و API خواندنی محدود است. الگوی repository مستقل، چندردیفی، رزرو سفارش فروش، FIFO خودکار، آپلود فایل، نمودار تعاملی و همگام‌سازی بین نصب‌ها در این بسته وجود ندارد. جزئیات سازگاری و آزمون اجراشده در گزارش‌های همراه ثبت شده‌اند.
