# PHPForge v1.3: semantic routing and evaluation guidance

Use this reference only when changing PHPForge's router, context selection, risk model, dataset/evaluator, benchmarks, or release/readiness claims. It distills the supplied v1.3 brief; these are requirements and targets, not evidence that the current v1.2 package already satisfies them.

## Runtime decisions

Represent the task's main issue, requested action, constraints, environment, distractors, explicit exclusions, and risk signals separately before selecting domain context. Evaluate sentence-level relevance so a causal issue outweighs incidental testing, framework, deployment, performance, or README details. Test false user hypotheses against behavioral evidence.

Keep domain, concept, risk, scope, and context selection separate. Support more than one material concept and use a concept family when the exact child is uncertain. A domain mention does not by itself expand scope or activate every module. Explain why relevant context was selected and why tempting but irrelevant context was suppressed.

For security, reason through assets, actors, entry points, trust boundaries, sources, sinks, authorization boundaries, exploit conditions, and impact. For financial behavior, identify state and money movement, invariants, operation identity, retries, concurrency, state transitions, settlement/reconciliation, and event ordering. Distinguish duplicate, replayed, late, lost, retried, and out-of-order events when evidence supports those concepts.

Treat router confidence as heuristic unless it has been calibrated against suitable independent labels. Prefer recall for critical security and financial risks, but report precision and under-classification too. Do not infer permission for high-risk autonomous actions from a routing label.

## Independent evaluation boundary

Keep runtime and evaluation as separate knowledge worlds:

- The runtime may use `manifests/module-registry.yaml` to route work.
- Dataset authoring and hidden/holdout wording must not be derived from that registry, its aliases, or expected concepts. The generator must not import or read the runtime registry to construct cases.
- The runtime must not import expected labels or benchmark-only metadata. Invoke it as a black box and give only its output to the evaluator.
- Keep development, validation, external holdout, and blind red-team data separate. Freeze holdout data and expected labels before scoring; change a frozen case only for a documented malformed case or objectively incorrect label, with an audit record.
- Store provenance with each evaluation case, but keep evaluator-only labels and metadata inaccessible to the runtime.

Use an automated firewall to check these boundaries and make a failure block a release claim. Track exact domain, concept-family, exact-concept, critical-risk, exact/near risk, scope, multi-concept, and irrelevant-context behavior where labels support those measures. Include confusion matrices and failure clusters; do not let aggregate pass counts conceal systematic errors.

## Evidence and release claims

Treat the v1.3 brief's corpus sizes, recall targets, risk-calibration sample, and agent A/B task count as acceptance targets. They are not completed measurements. A production claim needs frozen external and post-freeze blind results, transparent sample sizes and uncertainty, and no material critical-risk under-classification. The brief also calls for a same-model, same-repository, same-task baseline-versus-PHPForge agent comparison with blind output scoring; self-assessment or a stub runner is not that evidence.

Measure tokens only with the actual deployment tokenizer/runtime. Character counts are character counts, not token savings. Report input, routed context, output, and total tokens alongside task quality; do not claim an improvement from an unexecuted adapter or synthetic estimate.

The supplied v1.2 reports state: 1,610 normalized-unique cases; 262/262 hidden required-condition passes; 173/200 (86.5%) blind red-team passes; 27 blind failures; and no verified independent agent A/B or deployment-tokenizer measurement. They classify the release as pilot, not production-ready. Recheck the current reports before repeating any figures, and do not promote these v1.2 results into v1.3 evidence.
