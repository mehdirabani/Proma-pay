## هدف این دامنه

دامنه **Users & Roles** مسئول مدیریت کاربران داخلی سیستم است.

کاربران داخلی شامل افراد زیر هستند:

- مدیر اصلی
- مدیر سامانه
- مدیر واحد
- کارمند
- اپراتور
- وکیل یا مسئول حقوقی
- حسابدار
- پشتیبان
- کاربر سیستمی برای عملیات خودکار

این دامنه مشخص می‌کند:

- چه کسی وارد پنل داخلی می‌شود.
- هر کاربر چه نقشی دارد.
- هر نقش چه دسترسی‌هایی دارد.
- هر کاربر به کدام داده‌ها دسترسی دارد.
- چه کسی می‌تواند کاربران دیگر را مدیریت کند.
- چه عملیاتی باید Audit و Security Log داشته باشد.

## تفاوت User و Customer

در Proma Pay، **User** و **Customer** دو مفهوم جدا هستند.

### User

کاربر داخلی سیستم است.

مثال:

- مدیر
- اپراتور
- وکیل
- حسابدار
- پشتیبان
- مدیر واحد

### Customer

مشتری فروشگاه است.

مشتری:

- قرارداد دارد.
- قسط پرداخت می‌کند.
- مدرک هویتی آپلود می‌کند.
- فقط داده‌های خودش را می‌بیند.
- در صفحه Users نمایش داده نمی‌شود.

### قانون مهم

مشتری نباید در صفحه Users نمایش داده شود.  
کاربر داخلی هم نباید در صفحه Customers نمایش داده شود، مگر اینکه واقعاً یک رکورد مشتری جداگانه برای او ساخته شده باشد.

## تعریف نقش‌ها

### super_admin

مدیر اصلی سیستم است.

می‌تواند:

- کاربران را مدیریت کند.
- نقش‌ها را مدیریت کند.
- Permissionها را مدیریت کند.
- تنظیمات حساس را تغییر دهد.
- بکاپ بگیرد.
- Restore انجام دهد.
- آپدیت اجرا کند.
- پلاگین نصب و غیرفعال کند.
- لاگ‌های حساس را ببیند.

قانون:

- عملیات حساس super_admin همیشه باید Audit Log داشته باشد.
- حذف یا غیرفعال کردن تنها super_admin سیستم ممنوع است.

---

### admin

مدیر سامانه یا فروشگاه است.

می‌تواند طبق Permission:

- کاربران داخلی را مدیریت کند.
- مشتریان را ببیند.
- قراردادها را مدیریت کند.
- گزارش‌ها را مشاهده کند.
- پرداخت‌ها را بررسی کند.
- تنظیمات عمومی را تغییر دهد.

ممکن است برخی عملیات فقط برای super_admin مجاز باشد، مثل:

- Restore بکاپ
- تغییر Permissionهای اصلی
- اجرای آپدیت Core
- حذف لاگ‌های حساس
- حذف پلاگین‌های مهم

---

### department_manager

مدیر یک واحد سازمانی است.

می‌تواند:

- کاربران همان واحد را ببیند.
- فعالیت‌های همان واحد را مدیریت کند.
- گزارش‌های همان واحد را ببیند.
- وظایف همان واحد را پیگیری کند.

نمی‌تواند:

- کاربران واحدهای دیگر را ببیند.
- کاربران خارج از واحد خودش را ویرایش کند.
- تنظیمات کل سیستم را تغییر دهد، مگر Permission داشته باشد.

---

### staff

کارمند داخلی است.

دسترسی staff باید کاملاً بر اساس Permission تعریف شود.

این نقش نباید دسترسی آزاد یا پیش‌فرض گسترده داشته باشد.

---

### operator

اپراتور پیگیری اقساط است.

اپراتور می‌تواند:

- اقساط سررسید گذشته مجاز را ببیند.
- با مشتری تماس بگیرد.
- شماره تماس مشتری و ضامن را در حد نیاز ببیند.
- نتیجه پیگیری را ثبت کند.
- وعده پرداخت ثبت کند.
- در صورت داشتن Permission پرونده را به حقوقی ارجاع دهد.
- با مشتریان مجاز گفتگو کند.

اپراتور نمی‌تواند:

- صفحه Users را ببیند.
- کاربران داخلی را مدیریت کند.
- قرارداد را حذف کند.
- پرداخت را تأیید کند.
- رسید پرداخت را تأیید یا رد کند.
- تنظیمات سیستم را تغییر دهد.
- گزارش مالی کامل ببیند.
- مدارک هویتی حساس را بدون Permission ببیند.

---

### lawyer

کاربر واحد حقوقی است.

وکیل می‌تواند:

- پرونده‌های ارجاع‌شده را ببیند.
- پرونده‌های آماده شکایت را ببیند.
- پرونده‌های شکایت‌شده را مدیریت کند.
- مرحله حقوقی ثبت کند.
- هزینه حقوقی ثبت کند.
- فایل حقوقی آپلود کند.
- جلسه دادگاه ثبت کند.
- مشتری و قرارداد مرتبط با پرونده مجاز را ببیند.

وکیل نمی‌تواند:

- همه مشتریان را بدون ارتباط حقوقی ببیند.
- تنظیمات مالی را تغییر دهد.
- پرداخت را تأیید کند.
- کاربران را مدیریت کند، مگر Permission داشته باشد.

---

### accountant

مسئول مالی است.

می‌تواند طبق Permission:

- پرداخت‌ها را ببیند.
- گزارش‌های مالی را ببیند.
- وضعیت اقساط را بررسی کند.
- تسویه‌ها را مشاهده کند.
- هزینه‌های حقوقی را ببیند.
- گزارش وصولی را بررسی کند.

تأیید پرداخت فقط در صورت داشتن Permission مجاز است.

---

### support

پشتیبانی است.

می‌تواند:

- گفتگوهای مجاز را ببیند.
- به مشتریان پاسخ دهد.
- اطلاعات پایه مشتری را در حد نیاز ببیند.
- یادداشت پشتیبانی ثبت کند.

نمی‌تواند:

- اطلاعات مالی حساس را ببیند، مگر Permission داشته باشد.
- پرداخت را تأیید کند.
- تنظیمات را تغییر دهد.
- مدارک هویتی حساس را بدون Permission ببیند.

---

### system

نقش داخلی برای عملیات خودکار سیستم است.

نمونه عملیات:

- Cron Job
- Cleanup Job
- ارسال Reminder
- ارسال Notification
- Backup Scheduler
- Update System
- پاکسازی فایل‌های منقضی‌شده

قانون:

هر عملیات system باید Log داشته باشد و actor آن مشخص باشد:

`actor = system`

## وضعیت‌های کاربر

وضعیت‌های اصلی:

| وضعیت       | توضیح                                 |
| ----------- | ------------------------------------- |
| `active`    | کاربر فعال است                        |
| `inactive`  | کاربر غیرفعال است                     |
| `suspended` | کاربر تعلیق شده است                   |
| `deleted`   | کاربر به صورت Soft Delete حذف شده است |

### قوانین وضعیت

- کاربر inactive نباید بتواند وارد سیستم شود.
- کاربر suspended نباید بتواند وارد سیستم شود.
- کاربر deleted نباید در لیست عادی کاربران نمایش داده شود.
- تغییر وضعیت کاربر باید Audit Log داشته باشد.
- بعد از غیرفعال‌سازی یا تعلیق کاربر، Sessionهای فعال او باید باطل شوند.

- Settings Update

## Scopeهای دسترسی

| Scope            | توضیح                     |
| ---------------- | ------------------------- |
| `all`            | دسترسی به همه داده‌ها     |
| `own`            | فقط داده‌های خودش         |
| `assigned`       | فقط داده‌های ارجاع‌شده    |
| `department`     | فقط داده‌های واحد خودش    |
| `legal_assigned` | فقط پرونده‌های حقوقی مجاز |
| `readonly`       | فقط مشاهده                |
| `none`           | بدون دسترسی               |

مثال:

| Permission     | Scope        | معنی                     |
| -------------- | ------------ | ------------------------ |
| `users.view`   | `all`        | مشاهده همه کاربران       |
| `users.view`   | `department` | مشاهده کاربران همان واحد |
| `users.update` | `department` | ویرایش کاربران همان واحد |
| `users.delete` | `none`       | بدون اجازه حذف           |

## مدیریت نقش‌ها

مدیریت Role بسیار حساس است.

قوانین:

- فقط کاربران مجاز می‌توانند نقش بسازند.
- فقط کاربران مجاز می‌توانند نقش را تغییر دهند.
- Roleهای سیستمی نباید بدون بررسی حذف شوند.
- تغییر Permissionهای یک Role باید Audit Log داشته باشد.
- تغییر Role کاربر باید Audit Log داشته باشد.
- اگر Role کاربر تغییر کرد، Permission Cache باید باطل شود.
- اگر سطح دسترسی کاربر کاهش یافت، Sessionهای فعال باید بررسی یا باطل شوند.

---

## مدیریت Permissionها

Permissionها باید مرکزی مدیریت شوند.

قوانین:

- Permission نباید پراکنده و Hardcode شده باشد.
- Permissionهای اصلی باید در دیتابیس یا Registry رسمی سیستم ثبت شوند.
- Permissionهای پلاگین باید از طریق Plugin Manager ثبت شوند.
- حذف Permission فعال باید محدود شود.

## Workflowها

### ایجاد کاربر داخلی

1. مدیر وارد صفحه Users می‌شود.
2. Permission بررسی می‌شود.
3. فرم ایجاد کاربر تکمیل می‌شود.
4. اطلاعات Validation می‌شوند.
5. تکراری نبودن username، email و mobile بررسی می‌شود.
6. رمز عبور با `password_hash` ذخیره می‌شود.
7. نقش و واحد ثبت می‌شود.
8. Permission اختصاصی در صورت نیاز ثبت می‌شود.
9. Audit Log ثبت می‌شود.
10. Toast موفقیت نمایش داده می‌شود.

---

### ویرایش کاربر داخلی

1. فرم ویرایش باز می‌شود.
2. Permission بررسی می‌شود.
3. Scope داده بررسی می‌شود.
4. اطلاعات Validation می‌شوند.
5. تغییرات ذخیره می‌شوند.
6. اگر Role یا Permission تغییر کرد، Permission Cache باطل می‌شود.
7. اگر status به inactive یا suspended تغییر کرد، Sessionهای فعال باطل می‌شوند.
8. Audit Log با old_values و new_values ثبت می‌شود.
9. Toast موفقیت نمایش داده می‌شود.

---

### حذف یا غیرفعال‌سازی کاربر

1. درخواست حذف یا غیرفعال‌سازی ثبت می‌شود.
2. Permission بررسی می‌شود.
3. وابستگی‌های کاربر بررسی می‌شود.
4. Confirmation Modal نمایش داده می‌شود.
5. اگر عملیات حساس بود، عبارت تأیید دریافت می‌شود.
6. کاربر Soft Delete یا inactive می‌شود.
7. Sessionهای فعال باطل می‌شوند.
8. Audit Log ثبت می‌شود.

عبارت تأیید:

`حذف را تایید می‌کنم`

## محدودیت‌های حذف کاربر

حذف یا غیرفعال‌سازی کاربر باید با احتیاط انجام شود اگر:

- پرونده حقوقی فعال دارد.
- پیگیری فعال دارد.
- رویداد تقویم فعال دارد.
- وظیفه باز دارد.
- تنها super_admin سیستم است.
- مدیر یک واحد فعال است.

در این حالت سیستم باید هشدار دهد و در صورت نیاز پیشنهاد انتقال وظایف به کاربر دیگر بدهد.
