# اتصال امن کانال فروشگاه به افزونه‌های موجود — فاز ۸

## وضعیت

این فاز لایهٔ انتشار رویدادهای چرخهٔ درخواست WooCommerce را از طریق `SystemOutbox` و `PluginManager` اضافه می‌کند. هیچ درخواست در انتظار بررسی به قرارداد، فروش حسابداری، پاداش، رزرو موجودی یا تعهد پرداخت تبدیل نمی‌شود. اتصال عملیاتی هر افزونه فقط پس از فراهم‌شدن داده و تأییدهای لازم مجاز است.

## رویدادهای داخلی

| رویداد | زمان انتشار | دادهٔ قابل دسترس برای listener |
|---|---|---|
| `merchant_api.order.pending_review` | بعد از ثبت موفق و یک‌بارمصرف سفارش | شناسهٔ داخلی سفارش، شناسه‌های فروشنده/سایت/اتصال، هش شناسهٔ خارجی، وضعیت |
| `merchant_api.contract_request.pending_review` | بعد از ثبت درخواست قرارداد | همان داده‌ها و UUID داخلی درخواست |
| `merchant_api.order.cancelled` | بعد از لغو مجاز سفارش معلق | همان داده‌ها و کد دلیل لغو |

رویدادها از outbox موجود صف می‌شوند، سپس در زمینهٔ worker به hookهای افزونه‌های فعال می‌رسند. `outbox_event_id` شناسهٔ تلاش منطقی را در اختیار مصرف‌کننده می‌گذارد؛ مصرف‌کننده باید در برابر تحویل مجدد idempotent باشد. payload شامل شناسهٔ خام سفارش فروشگاه، اطلاعات هویتی مشتری، مبلغ، رمز یا اجازهٔ ثبت مالی نیست و صریحاً `financial_posting_permitted=false` دارد.

## نقشهٔ افزونه‌ها و مرز مجاز

| افزونه | قابلیت موجود قابل استفاده | مرز اتصال کانال فروشگاه در این نسخه |
|---|---|---|
| PromaAccounting | رویدادهای واقعی `contract.created/updated/cancelled` به فروش و کمیسیون متصل‌اند | سفارش معلق، قرارداد قطعی یا طلب نیست؛ برای جلوگیری از ثبت درآمد/کمیسیون زودهنگام به دفترکل ارسال نمی‌شود |
| PromaAffiliate | نسبت‌دادن مشتری/معرف برای قرارداد واقعی و پاداش پس از trigger تعریف‌شده | API فقط هش مرجع مشتری بیرونی را نگه می‌دارد و شناسهٔ داخلی مشتری/معرف ندارد؛ هیچ پاداشی صادر نمی‌شود |
| PromaInventoryPartners | مدیریت انبار، شریک و گردش موجودی مستقل | درخواست API فاقد SKU، انبار و نگاشت کالا است؛ موجودی رزرو یا کسر نمی‌شود |
| PromaSignConnect | hookهای قرارداد واقعی برای رویدادهای ایجاد، تغییر و لغو | درخواست معلق قرارداد قابل امضا نیست؛ ارسال امضا یا پیام خودکار انجام نمی‌شود |
| PromaZarinpal | درگاه دریافت پلتفرم و provider گزارش تراکنش خودش | پیش‌پرداخت فروش Woo باید از درگاه انتخابی فروشنده عبور کند؛ افزونهٔ مرکزی به‌جای آن انتخاب یا برداشت نمی‌کند |
| PromaRepair | چرخهٔ مستقل تعمیر دستگاه | رابطه‌ای با خرید اقساطی ندارد؛ پروندهٔ تعمیر از سفارش فروشگاه ساخته نمی‌شود |

## پیش‌نیازهای فعال‌سازی downstream

1. مسیر بررسی انسانی که مشتری داخلی را با مجوز مشخص به مرجع مشتری فروشگاه پیوند دهد؛ نگهداری hash به‌تنهایی برای تطبیق کافی نیست.
2. ساخت قرارداد واقعی پس از بررسی هویت، پذیرش شرایط، تأیید ضمانت و کنترل تاریخ اولین قسط.
3. نگاشت SKU/variation فروشگاه به کالای داخلی و سیاست موجودی برای InventoryPartners.
4. قرارداد مالی و حقوقی تأییدشده برای شناسایی فروش، کمیسیون، طلب، نقدینگی و تسویه؛ ماندهٔ وصول‌نشده وجه نقد نیست.
5. تعریف trigger و مسئول مجاز برای referral، امضای قرارداد و لغو/مرجوعی.

تا زمان تحقق این پیش‌نیازها، اتصال‌های بالا در نقشهٔ معماری ثبت‌اند اما side effect مالی/عملیاتی ندارند. این محدودیت، بلوکهٔ تجاری/حقوقی فعال‌سازی کامل Phase 8 است.

## اعتبارسنجی

- تست واحد payload، tenant scope، هش شناسهٔ بیرونی، allowlist رویداد و عدم افشای شناسه/مبلغ/PII در `tests/merchant_plugin_integration_phase8.php`.
- تست integration روی پایگاه‌دادهٔ disposable بررسی می‌کند ایجاد سفارش، درخواست قرارداد و لغو، hookهای outbox را یک‌بار و بدون دادهٔ حساس صف می‌کنند.
- رویدادهای pending عمداً به `contract.created` یا عملیات دفترکل ترجمه نمی‌شوند.
