# برنامهٔ مهاجرت امن PromaInventoryPartners

## اصل داده

این مهاجرت ETL به schema تازه نیست. افزونهٔ جدید باید همان جداول `plugin_inventory_*` را که افزونهٔ قدیمی ایجاد کرده، مرجع واحد موجودی، فروش و دفترکل نگه دارد. migration افزونهٔ جدید فقط وجود schema را با `CREATE TABLE IF NOT EXISTS`/تغییر افزایشی می‌سنجد و جداول کالا/فروش/پرداخت/journal موازی نمی‌سازد. این کار شناسه‌ها، IMEIها، محموله‌ها، معاملات و journalهای تاریخی را بدون کپی حفظ می‌کند.

## مراحل

1. **ثبت مبنا** — در backup و گزارش، نسخهٔ هسته/افزونه، زمان snapshot، وضعیت migration و تعداد/جمع دادهٔ جداول عملیاتی با `plugins/PromaPartnershipLedger/tools/migration-snapshot.sql` ثبت شود. جدول‌های Registry، مجوزها، قسط/پرداخت core نیز ثبت شوند.
2. **نسخهٔ پشتیبان** — snapshot دیتابیس و فایل‌ها تهیه و بازیابی آن در محیط جداگانه تأیید شود. در زمان تهیهٔ مبنا، نوشتن عملیات در سامانه متوقف یا بازهٔ تراکنشی آن ثبت شود.
3. **نصب آزمایشی successor** — بسته روی staging نصب شود. migrationها باید جدول‌های موجود را حفظ کنند. افزونهٔ قدیمی در این مرحله تنها writer فعال بماند؛ successor در حالت غیرفعال/آمادهٔ بررسی بماند.
4. **تطبیق read-only** — تعداد کالا، محموله، ماندهٔ مقداری و ریالی، سریال‌ها و وضعیتشان، خرید/فروش/مرجوعی، آورده، سهم سرمایه، journalهای بدهکار/بستانکار، تخصیص پرداخت، هزینه و تسویه با شناسه و جمع کنترل شوند. چون هر دو نسخه از یک schema استفاده می‌کنند، اختلاف شناسه/جمع باید صفر باشد؛ مقدار مجهول با صفر جایگزین نشود.
5. **آزمون برابری قابلیت** — ماتریس parity و آزمون‌های مالی/سریال/رقابت اجرا شوند. تمام نتایج و خروجی queryها به گزارش تطبیق ضمیمه شوند.
6. **Cutover کنترل‌شده** — پس از گزارش و تأیید مسئول داده، در پنجرهٔ نگهداری، افزونهٔ قدیمی غیرفعال و سپس افزونهٔ جدید فعال شود. guard افزونه باید از فعال‌بودن هم‌زمان دو provider جلوگیری کند. هیچ انتقالی با dual-write انجام نشود.
7. **اعتبارسنجی** — اجرای smoke read-only، فروش تستی staging، event پرداخت، تطبیق دفتر، گزارش شریک و ماندهٔ موجودی. محیط Production تا رفع اختلاف/خطای مسدودکننده از وضعیت «آماده» برخوردار نیست.
8. **بازنشستگی** — فقط پس از تأیید کتبی تطبیق و دورهٔ پایش، منوی قدیمی کنار گذاشته شود. uninstall/purge و حذف جداول قدیمی جزو cutover نیست.

## قواعد توقف

- هر اختلاف در سریال/IMEI، تعداد یا بهای lot، journal نامتوازن، پرداخت تکراری، ماندهٔ سرمایه/تسویه، یا hook تکراری cutover را متوقف می‌کند.
- نبود دسترسی دیتابیس/staging به معنی «تطبیق‌نشده» است، نه «بدون اختلاف».
- hook اصلاح پرداخت در core فعلاً یافت نشده؛ تا اضافه‌شدن adapter معتبر، پس از اصلاح پرداخت تطبیق مجاز دستی لازم است.
- permissionهای role ممکن است به کلید plugin id وابسته باشند؛ نقش‌ها باید از `proma-inventory-partners.*` به `proma-partnership-ledger.*` نگاشت و با کاربر واقعی بررسی شوند.

## برنامهٔ بازگشت

در صورت بروز خطا: نوشتن را متوقف کنید، successor را غیرفعال کنید، وضعیت eventها و رکوردهای بعد از cutover را ثبت/تطبیق دهید، سپس افزونهٔ قدیمی را فعال کنید. چون جدول‌های عملیاتی مشترک هستند، بازگشت کد به نسخهٔ قدیمی نیازمند rollback دیتابیس نیست. migrationهای افزایشی جدید حذف نمی‌شوند و رویدادهای جدید پاک نمی‌شوند. بازگشت صرف به backup پیش از cutover مجاز نیست مگر تراکنش‌های بعدی جداگانه بازپخش/تطبیق شوند.

## وضعیت فعلی

تا زمانی که baseline از دیتابیس staging/واقعی و نتیجهٔ هر مرحله ضمیمه نشده، migration اجراشده یا تأییدشده محسوب نمی‌شود. افزونهٔ قدیمی در این کار غیرفعال یا حذف نمی‌شود.
