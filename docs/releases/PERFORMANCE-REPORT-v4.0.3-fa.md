# گزارش عملکرد Proma Pay V4.0.3 — Candidate

## شواهد اندازه‌گیری‌شده‌ی قبلی

برای مسیر فهرست مشتریان، دو نمونه‌ی QA قبلی با ۳۰ درخواست گرم روی هر اجرا ثبت شده است: پیش از بهینه‌سازی و پس از آن. داده‌ها در `docs/performance/QA_HTTP_BASELINE.json`, `QA_SERVER_BASELINE.json`, `QA_CUSTOMERS_AFTER.json` و `QA_CUSTOMERS_SERVER_AFTER.json` هستند.

| شاخص مشتریان | پیش از بهینه‌سازی | پس از بهینه‌سازی | تغییر محاسبه‌شده |
|---|---:|---:|---:|
| زمان wall p95 | 439.99 ms | 100.03 ms | 77.3٪ کمتر |
| زمان PHP p95 | 431.19 ms | 88.29 ms | 79.5٪ کمتر |
| تعداد Query p95 | 1,100 | 45 | 95.9٪ کمتر |
| زمان SQL p95 | 359.68 ms | 54.25 ms | 84.9٪ کمتر |

در هر اجرا ۳۰ درخواست HTTP موفق گزارش شده است. این نتیجه مربوط به مسیر مشتریان و محیط کوچک QA قبلی است؛ نتیجه‌ی آن را به کل سامانه یا تغییرهای V4.0.3 نسبت نمی‌دهیم.

## ارزیابی V4.0.3

بنچمارک جدید Candidate اجرا نشد. P50/P95/P99 فعلی، بار هم‌زمان، حافظه‌ی V4.0.3، LCP/INP/CLS، زمان محاسبات حقوقی/مالی و تولید گزارش در این مرحله اندازه‌گیری نشده‌اند. کاهش ۳۰٪ هدف است، نه نتیجه‌ی این release.

گام بعد: روی DB clone با seed ثابت، ۳۰+ درخواست گرم برای داشبورد، فهرست مشتریان، قرارداد، اقساط، معوقات، حقوقی، حسابداری و پنل مشتری؛ سپس اجرای بار هم‌زمان و ثبت telemetry و browser timings. پیش از/پس باید PHP، DB، seed، route، warmup و concurrency یکسان بمانند.
