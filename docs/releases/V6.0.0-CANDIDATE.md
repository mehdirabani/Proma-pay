# Proma Pay V6.0.0 — Candidate

This release candidate contains a full Core ZIP and a differential update ZIP built against the V5.0.5 Core package. It is not a production-certified release. The current source tree contains prior local work, so the package builder records a source-status fingerprint in the candidate manifest.

## V6 changes

- Existing contract balance calculation now has one public V6 entry point, `FinancialDebtEngine`; the former `ContractFinancialSummaryService` remains as a compatibility adapter.
- New payments, grouped allocations, approved referred legal costs, and supported payment corrections append integer-Toman events to `financial_ledger_events` and `financial_ledger_lines`. Idempotency keys prevent a retry from writing a second event. Existing allocations, settlement quotes, contract locks, and payment priority remain the operating calculation and allocation policy.
- Admins can calculate an explainable Proma Score from recorded customer history, review the evidence behind it, and configure weights. Recommendations are advisory. Returned-check data is explicitly marked unavailable because this installation has no authoritative source table.
- The collection center reuses the current overdue aggregation and legal eligibility policy. It shows critical debt, today's promises, contracts without recent contact, legal-review candidates, and a combined contract timeline. A token-protected daily cron route or an admin action runs stage progression to create idempotent operator tasks and in-app notices; it does not automatically file legal actions or send SMS.
- Settings can make contract-wide payment forms default to legal-cost-first allocation; the remaining funds follow the established installment policy. Per-installment component ordering is not a free-form settings permutation in V6.
- Admins can broadcast an in-app announcement to all active users or selected active roles. Each recipient has an independent read state.
- Existing manager-signature upload and seller-signature injection into installment contracts are retained.

## Data and financial limitations

The V6 migration is additive. It does not fabricate historical payment events or backfill a ledger opening balance. Historical balances continue to be calculated from the existing contract, installment, payment, and approved legal-cost records through the centralized debt engine. Journal events begin when V6 code records a supported financial action. Operators must reconcile the live debt read model against journal events before using journal totals as a standalone accounting balance.

The journal records customer receivable bucket movements. It is not a full double-entry general ledger, and no claim is made that all legacy adjustment, discount, write-off, or import pathways are journaled yet. A future production release must close this reconciliation gap, backfill a reviewed opening balance, and pass race, recovery, and database integration tests on the supported MySQL/MariaDB versions.

## Install and update

- Fresh install: use `core/PromaPay-v6.0.0.zip` from the candidate output and configure a new database. The installer includes the V6 schema.
- Existing V5.0.5: use only the update ZIP whose manifest requires V5.0.5. The updater takes its safety backup before applying files and the additive SQL migration.
- Do not install this V6 package over a different baseline by renaming the ZIP. Use a compatible update package or install the full Core in a separate, empty application root.

## Rollback

The migration creates tables and MySQL DDL is not transactionally reversible. If an update fails after migration execution starts, preserve the updater's safety backup and restore the database and application files from the same pre-update backup set. Do not restore only old PHP files while retaining a partially migrated database. Test restoration on a copy before using it on a live host.
