# ممیزی فیلتر، مرتب‌سازی و صفحه‌بندی — نسخه 1.5.3

## علت‌های ریشه‌ای یافت‌شده

| بخش | علت | اصلاح |
|---|---|---|
| صفحه‌بندی اقساط | View حلقهٔ همهٔ شماره صفحات را مستقیم می‌ساخت، با وجود تابع مشترک Ellipsis | استفاده از `render_pagination()` |
| فیلتر اقساط | تغییر کنترل‌ها صفحهٔ قبلی را نگه می‌داشت | `data-filter-reset-page` و reset سمت JavaScript؛ نرمال‌سازی سرور برای صفحهٔ خارج از بازه |
| اقساط پرداخت‌شده | از فهرست عملیاتی جدا و داخل `details` بود | تب مستقل `paid` و نتیجهٔ سروری مستقل |
| صف سررسید | داده در سطح قسط صفحه‌بندی می‌شد، پس یک قرارداد تکرار می‌شد | `OverdueAggregationService` با `GROUP BY contract_id` قبل از count/order/page |
| مرتب‌سازی سررسید | معیارهایی مانند تعداد قسط معوق روی ردیف قسط معنا نداشتند | sort whitelist روی aggregateهای `overdue_count`، `max_overdue_days` و `estimated_payable` |
| ورودی URL | مقادیر GET مستقیماً به منطق پراکنده می‌رسیدند | `OverdueFilterCriteria` با whitelist، تاریخ جلالی، ارقام فارسی و بازه‌های امن |

## رفتار تضمین‌شده

- تغییر فیلتر یا مرتب‌سازی صفحه را به ۱ بازمی‌گرداند.
- صفحهٔ غیرمعتبر سرور به آخرین صفحهٔ معتبر نرمال می‌شود.
- لینک‌های صفحه‌بندی، تب، جست‌وجو، مرتب‌سازی و اندازهٔ صفحه را حفظ می‌کنند.
- مرتب‌سازی فقط در سرور انجام می‌شود و هیچ نام ستون خامی از URL پذیرفته نمی‌شود.
- گزینهٔ «امروز» عمداً از سررسیدهای گذشته جداست تا شرط `due_date < CURDATE()` با `due_date = CURDATE()` تداخل نکند.

## شاخص‌های پرس‌وجو

صف سررسید از indexهای موجود `installments(contract_id,status,due_date)` و ارتباط‌های `contracts.customer_id/status`، `legal_cases(contract_id,status)` بهره می‌برد. count و page از یک subquery aggregate مشترک استفاده می‌کنند تا total با نتیجهٔ صفحه همخوان باشد. پیش از هر index جدید، EXPLAIN روی دادهٔ واقعی میزبان باید ثبت شود؛ در این انتشار index حدسی افزوده نشده است.
