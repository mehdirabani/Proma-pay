## هدف Workflow

هدف این Workflow این است که مشتری یا کاربر داخلی مجاز بتواند یک قسط را پرداخت کند و سیستم بعد از تأیید پرداخت، وضعیت قسط، قرارداد، گزارش‌ها، Timeline، Notification و Logهای مالی را به‌روزرسانی کند.

این Workflow باید پرداخت کامل و پرداخت ناقص را پشتیبانی کند.

پرداخت کارت‌به‌کارت و بررسی رسید در فایل جداگانه مستند می‌شود:

```text
docs/workflows/04_CARD_TO_CARD_REVIEW.md
```

## بازیگران

| بازیگر | نقش |
|---|---|
| Customer | پرداخت قسط خودش |
| Admin | مشاهده و مدیریت پرداخت‌ها |
| Accountant | ثبت یا بررسی پرداخت دستی در صورت Permission |
| Operator | مشاهده وضعیت پرداخت برای پیگیری |
| Payment Gateway | پردازش پرداخت آنلاین |
| Financial System | محاسبه مبلغ قابل پرداخت |
| Notification System | ارسال اعلان نتیجه پرداخت |
| Chat Bot | ارسال پیام سیستمی به مشتری |

## پیش‌نیازها

قبل از اجرای این Workflow باید موارد زیر آماده باشند:

- قرارداد فعال باشد.
- قسط معتبر وجود داشته باشد.
- قسط cancelled یا deleted نباشد.
- مشتری مالک قسط باشد.
- Payment Settings فعال باشد.
- درگاه پرداخت در صورت استفاده فعال و تنظیم شده باشد.
- Financial Calculation Service آماده باشد.
- CSRF فعال باشد.
- Permissionهای پرداخت و ثبت پرداخت دستی تعریف شده باشند.

- installment_id

- اطلاعات لازم برای درگاه در صورت نیاز

- customer_id

- amount
- payment_date

- description
- فایل یا سند در صورت نیاز

## خروجی‌ها

خروجی‌های این Workflow:

- ایجاد رکورد Payment
- تأیید یا رد پرداخت
- بروزرسانی paid_amount قسط
- بروزرسانی remaining_amount قسط
- تغییر وضعیت قسط به paid یا partially_paid
- بروزرسانی خلاصه مالی قرارداد
- ثبت Financial Log
- ثبت Timeline
- ارسال Notification
- ارسال Bot Message
- آماده‌سازی داده برای Reports

## وضعیت‌های پرداخت در این Workflow

| وضعیت | توضیح |
|---|---|
| `initiated` | پرداخت شروع شده |
| `waiting` | در انتظار نتیجه |
| `approved` | پرداخت تأیید شده |
| `failed` | پرداخت ناموفق |
| `cancelled` | پرداخت لغو شده |
| `expired` | پرداخت منقضی شده |
| `rejected` | پرداخت رد شده در حالت دستی یا بررسی |

---

## وضعیت‌های قسط بعد از پرداخت

| وضعیت | توضیح |
|---|---|
| `paid` | مبلغ قسط کامل پرداخت شده |
| `partially_paid` | بخشی از قسط پرداخت شده |
| `pending` | قسط هنوز پرداخت نشده |
| `overdue` | قسط معوق باقی مانده |
| `legal` | قسط در مسیر حقوقی است |

قانون:

پرداخت موفق همیشه الزاماً باعث paid شدن قسط نمی‌شود.  
اگر مبلغ پرداختی کمتر از مبلغ قابل پرداخت باشد، قسط باید `partially_paid` شود.

## مراحل اصلی Workflow

نمای کلی مراحل:

1. کاربر قسط را انتخاب می‌کند.
2. سیستم مالکیت و وضعیت قسط را بررسی می‌کند.
3. مبلغ قابل پرداخت از Financial Calculations دریافت می‌شود.
4. روش پرداخت انتخاب می‌شود.
5. Payment با وضعیت اولیه ایجاد می‌شود.
6. پرداخت آنلاین یا دستی پردازش می‌شود.
7. پرداخت اعتبارسنجی می‌شود.
8. پرداخت approved یا failed می‌شود.
9. مبلغ روی قسط اعمال می‌شود.
10. وضعیت قسط تغییر می‌کند.
11. Financial Log ثبت می‌شود.
12. Timeline، Notification و Bot Message ساخته می‌شود.
13. کاربر نتیجه را می‌بیند.

---

## انتخاب قسط برای پرداخت

### مراحل

1. مشتری وارد پنل اقساط خود می‌شود.
2. لیست اقساط خودش را می‌بیند.
3. قسط مورد نظر را انتخاب می‌کند.
4. سیستم Ownership Check انجام می‌دهد.
5. وضعیت قسط بررسی می‌شود.
6. اگر قسط قابل پرداخت بود، صفحه یا Modal پرداخت باز می‌شود.

### قوانین

- مشتری فقط اقساط خودش را ببیند.
- قسط paid نباید دوباره برای پرداخت کامل نمایش داده شود.
- قسط cancelled نباید قابل پرداخت باشد.
- قسط legal ممکن است طبق Settings یا Permission قابل پرداخت باشد.
- قسط مربوط به قرارداد غیرفعال نباید قابل پرداخت باشد.

## محاسبه مبلغ قابل پرداخت

مبلغ قابل پرداخت باید فقط از Financial Calculations Domain محاسبه شود.

### اجزای مبلغ

- مانده قسط
- جریمه دیرکرد در صورت وجود
- تخفیف قابل اعمال در صورت وجود
- اصلاحات مالی مجاز در صورت وجود

### قانون مهم

Frontend نباید منبع حقیقت مبلغ باشد.

ممنوع:

```php
$amount = $_POST['amount'];
```

صحیح:

```php
$amount = FinancialCalculationService::calculateInstallmentPayableAmount($installmentId);
```

---

## پرداخت آنلاین

### مراحل

1. مشتری روش پرداخت آنلاین را انتخاب می‌کند.
2. سیستم مبلغ نهایی را سمت سرور محاسبه می‌کند.
3. Payment با وضعیت `initiated` ایجاد می‌شود.
4. درخواست به درگاه پرداخت ارسال می‌شود.
5. Payment به وضعیت `waiting` می‌رود.
6. مشتری به صفحه درگاه منتقل می‌شود.
7. نتیجه از Callback درگاه دریافت می‌شود.

### قوانین

- درگاه باید از Settings یا Plugin رسمی خوانده شود.
- اطلاعات درگاه نباید Hardcode باشد.
- مبلغ ارسالی به درگاه باید از Backend محاسبه شود.
- هر Payment باید شناسه یکتا داشته باشد.
- پرداخت آنلاین بدون Callback معتبر نباید approved شود.

---

## Callback درگاه

Callback حساس‌ترین بخش پرداخت آنلاین است.

### مراحل

1. Gateway کاربر را به Callback URL برمی‌گرداند.
2. payment_id یا authority دریافت می‌شود.
3. Payment پیدا می‌شود.
4. وضعیت Payment بررسی می‌شود.
5. مبلغ پرداخت‌شده از Gateway تأیید می‌شود.
6. Transaction ID بررسی می‌شود.
7. تکراری نبودن تراکنش بررسی می‌شود.
8. اگر همه چیز معتبر بود، Payment approved می‌شود.
9. مبلغ روی قسط اعمال می‌شود.
10. کاربر به صفحه نتیجه پرداخت هدایت می‌شود.

### قوانین

- Callback باید Idempotent باشد.
- اگر Callback دوبار ارسال شد، پرداخت دوباره اعمال نشود.
- مبلغ Gateway باید با مبلغ مورد انتظار تطبیق داده شود.
- Transaction ID تکراری نباید پذیرفته شود.
- خطای Callback باید Gateway Log و Security Log داشته باشد.
- Listenerهای بعد از پرداخت نباید باعث دوباره اعمال شدن پرداخت شوند.

---

## ثبت پرداخت دستی

پرداخت دستی فقط توسط کاربر داخلی مجاز انجام می‌شود.

### کاربردها

- پرداخت نقدی در فروشگاه
- اصلاح پرداخت
- پرداخت ثبت‌شده خارج از درگاه
- پرداخت تأییدشده توسط حسابدار

### مراحل

1. کاربر داخلی وارد جزئیات قسط می‌شود.
2. گزینه ثبت پرداخت دستی را انتخاب می‌کند.
3. Permission بررسی می‌شود.
4. مبلغ و توضیح وارد می‌شود.
5. مبلغ توسط Backend اعتبارسنجی می‌شود.
6. Payment با method برابر `manual` ایجاد می‌شود.
7. در صورت مجاز بودن، Payment approved می‌شود.
8. مبلغ روی قسط اعمال می‌شود.
9. Financial Log و Audit Log ثبت می‌شود.
10. Notification برای مشتری ارسال می‌شود.

### قوانین

- پرداخت دستی باید Audit Log داشته باشد.
- پرداخت دستی باید دلیل یا توضیح داشته باشد.
- اپراتور معمولی نباید پرداخت دستی ثبت کند، مگر Permission داشته باشد.
- مبلغ دستی نباید باعث overpayment غیرمجاز شود.
- مشتری نباید بتواند پرداخت دستی برای خودش بسازد.

---

## پرداخت ناقص

پرداخت ناقص زمانی رخ می‌دهد که مبلغ پرداختی کمتر از مبلغ نهایی قابل پرداخت باشد.

### قوانین

- پرداخت ناقص می‌تواند approved شود.
- وضعیت قسط باید `partially_paid` شود.
- paid_amount افزایش یابد.
- remaining_amount کاهش یابد.
- مشتری باید مانده قابل پرداخت را ببیند.
- تخفیف تسویه کامل نباید روی پرداخت ناقص اعمال شود.
- Financial Log باید ثبت شود.

---

## جلوگیری از پرداخت تکراری

سیستم باید از پرداخت تکراری جلوگیری کند.

موارد بررسی:

- Payment قبلاً approved نشده باشد.
- قسط already paid نباشد.
- Transaction ID تکراری نباشد.
- Callback قبلاً پردازش نشده باشد.
- مبلغ قبلاً روی قسط اعمال نشده باشد.
- Request تکراری مشتری باعث ایجاد پرداخت قطعی تکراری نشود.

در صورت تشخیص پرداخت تکراری:

- عملیات متوقف شود.
- پیام مناسب نمایش داده شود.
- Security یا Payment Log ثبت شود.

---

## اعمال پرداخت روی قسط

اعمال پرداخت باید داخل Transaction انجام شود.

### مراحل

1. Payment approved می‌شود.
2. قسط Lock یا با کنترل همزمانی خوانده می‌شود.
3. paid_amount قبلی خوانده می‌شود.
4. مبلغ پرداختی به paid_amount اضافه می‌شود.
5. remaining_amount محاسبه می‌شود.
6. اگر remaining_amount صفر شد، قسط paid می‌شود.
7. اگر remaining_amount باقی ماند، قسط partially_paid می‌شود.
8. paid_at در صورت پرداخت کامل ثبت می‌شود.
9. Financial Log ثبت می‌شود.
10. Eventهای لازم Dispatch می‌شوند.

### قوانین

- قسط paid نباید دوباره paid شود.
- overpayment باید طبق Settings مدیریت شود.
- اعمال پرداخت باید atomic باشد.
- اگر اعمال پرداخت شکست خورد، Payment نباید approved نهایی بماند مگر وضعیت قابل بازیابی داشته باشد.

---

## Validationها

### قسط

- installment_id الزامی است.
- قسط باید وجود داشته باشد.
- قسط deleted نباشد.
- قسط cancelled نباشد.
- قسط متعلق به مشتری درست باشد.
- قسط paid نباشد، مگر overpayment یا پرداخت اضافه مجاز باشد.

### پرداخت

- amount باید عدد مثبت باشد.
- method معتبر باشد.
- Gateway فعال باشد، اگر روش آنلاین انتخاب شده است.
- Transaction ID نباید تکراری باشد.
- Payment قبلاً approved نشده باشد.
- payment_id معتبر باشد.
- مبلغ Frontend پذیرفته نشود.

### پرداخت دستی

- Permission لازم وجود داشته باشد.
- توضیح الزامی باشد.
- تاریخ پرداخت معتبر باشد.
- مبلغ باعث overpayment غیرمجاز نشود.

- اصلاح مانده قسط
- تشخیص overpayment

### Audit Log

موارد زیر Audit Log دارند:

- ثبت پرداخت دستی
- تغییر دستی وضعیت پرداخت
- اصلاح Payment
- لغو Payment
- تغییر مبلغ پرداخت توسط کاربر داخلی
- ثبت overpayment مجاز

---

### Security Log

موارد زیر Security Log دارند:

- Callback نامعتبر
- Transaction ID تکراری
- تلاش پرداخت قسط دیگران
- تلاش پرداخت قسط paid
- CSRF نامعتبر
- مبلغ دستکاری‌شده از Frontend
- تلاش ثبت پرداخت دستی بدون Permission

## خطاهای احتمالی

| خطا | رفتار مناسب |
|---|---|
| قسط پیدا نشد | نمایش پیام مناسب |
| قسط متعلق به مشتری نیست | Security Log و عدم دسترسی |
| قسط قبلاً پرداخت شده | نمایش پیام پرداخت شده |
| درگاه غیرفعال است | نمایش روش‌های دیگر |
| Callback نامعتبر است | failed یا waiting + Log |
| مبلغ Gateway ناسازگار است | عدم تأیید پرداخت + Security Log |
| Transaction تکراری است | جلوگیری از اعمال دوباره |
| پرداخت ناقص است | ثبت partially_paid |
| خطای اعمال پرداخت روی قسط | Rollback و ثبت Error Log |
| پرداخت دستی بدون Permission | Security Log و عدم دسترسی |

## تست‌های ضروری

### مسیر موفق آنلاین

- مشتری قسط خودش را انتخاب کند.
- مبلغ از Backend محاسبه شود.
- به درگاه منتقل شود.
- Callback معتبر دریافت شود.
- Payment approved شود.
- قسط paid شود.
- Notification و Timeline ثبت شود.

### پرداخت ناقص

- پرداخت کمتر از مبلغ قابل پرداخت ثبت شود.
- قسط partially_paid شود.
- remaining_amount درست محاسبه شود.
- تخفیف تسویه کامل اعمال نشود.

### پرداخت دستی

- کاربر مجاز پرداخت دستی ثبت کند.
- Audit Log ثبت شود.
- Financial Log ثبت شود.
- قسط بروزرسانی شود.

### تست‌های امنیتی

- مشتری نتواند قسط دیگران را پرداخت کند.
- مبلغ Frontend دستکاری‌شده پذیرفته نشود.
- Callback تکراری دوباره مبلغ را اعمال نکند.
- Transaction ID تکراری رد شود.
- کاربر بدون Permission نتواند پرداخت دستی ثبت کند.
