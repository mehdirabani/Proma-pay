## هدف Workflow

هدف این Workflow این است که مشتری، اپراتور، مدیر، حسابدار یا واحد حقوقی بتوانند در یک ساختار امن و قابل ردیابی با یکدیگر گفتگو کنند و پیام‌های سیستمی و ربات نیز در زمان‌های مناسب داخل گفتگوها ثبت شوند.

چت در Proma Pay فقط یک پیام‌رسان ساده نیست؛ بلکه باید به قرارداد، قسط، پرداخت، رسید، پرونده حقوقی، پیگیری معوقه و Timeline سیستم متصل باشد.

| Admin | مشاهده، مدیریت و ارجاع گفتگوها |

| Files System | مدیریت فایل‌های پیوست چت |
| Security System | کنترل دسترسی و ثبت تلاش‌های غیرمجاز |

## تعریف Chat Thread

Chat Thread یعنی یک گفتگو یا رشته پیام که می‌تواند بین مشتری و پشتیبانی، بین کاربران داخلی یا بین سیستم و مشتری باشد.

هر Thread می‌تواند به یک موجودیت مرتبط شود:

- customer
- contract
- installment
- payment
- legal_case
- support_ticket
- overdue_followup
- system_event

هر Thread باید حداقل این اطلاعات را داشته باشد:

- نوع گفتگو
- مشتری مرتبط در صورت وجود
- کاربر مسئول
- وضعیت
- آخرین پیام
- تعداد پیام‌های خوانده‌نشده
- سطح نمایش
- موجودیت مرتبط

---

## تعریف Bot Message

Bot Message پیامی است که توسط سیستم، بدون تایپ مستقیم کاربر، در چت ثبت می‌شود.

نمونه Bot Messageها:

- قرارداد جدید برای شما ثبت شد.
- قسط شما وارد وضعیت معوق شد.
- رسید پرداخت شما در انتظار بررسی است.
- رسید پرداخت شما تأیید شد.
- مدرک هویتی شما رد شد.
- پرونده شما وارد مرحله حقوقی شد.
- تسویه قرارداد شما انجام شد.

Bot Message باید قابل تشخیص از پیام کاربر باشد.

## مراحل اصلی Workflow

نمای کلی مراحل:

1. کاربر یا سیستم نیاز به گفتگو یا پیام ایجاد می‌کند.
2. Thread موجود پیدا می‌شود یا Thread جدید ساخته می‌شود.
3. Permission و Scope بررسی می‌شود.
4. پیام اعتبارسنجی می‌شود.
5. فایل پیوست در صورت وجود Validate و ذخیره می‌شود.
6. پیام ثبت می‌شود.
7. وضعیت Thread بروزرسانی می‌شود.
8. Notification برای گیرنده ارسال می‌شود.
9. شمارنده خوانده‌نشده بروزرسانی می‌شود.
10. Timeline موجودیت مرتبط ثبت می‌شود.
11. Log یا Audit در موارد حساس ثبت می‌شود.

---

## ایجاد گفتگو برای مشتری

### حالت‌های ایجاد گفتگو

گفتگو می‌تواند در شرایط زیر ایجاد شود:

- مشتری پیام جدید ارسال کند.
- قرارداد جدید ساخته شود.
- قسط معوق شود.
- رسید پرداخت ارسال شود.
- پرونده حقوقی ایجاد شود.
- اپراتور برای مشتری Thread بسازد.
- سیستم Bot Message ایجاد کند.

### قوانین

- برای هر مشتری می‌توان یک Thread عمومی پشتیبانی داشت.
- برای هر قرارداد می‌توان Thread جدا داشت.
- برای هر پرونده حقوقی می‌توان Thread محدود داشت.
- Thread تکراری برای یک related_type و related_id نباید بی‌دلیل ساخته شود.
- اگر Thread بسته شده باشد، بازگشایی باید طبق Settings انجام شود.

---

## ارسال پیام توسط مشتری

### مراحل

1. مشتری وارد پنل خودش می‌شود.
2. Thread مرتبط را انتخاب می‌کند یا پیام جدید می‌سازد.
3. متن پیام را وارد می‌کند.
4. فایل پیوست در صورت نیاز انتخاب می‌کند.
5. CSRF بررسی می‌شود.
6. Ownership Check انجام می‌شود.
7. پیام Validate می‌شود.
8. فایل در صورت وجود در Private Storage ذخیره می‌شود.
9. پیام در Thread ثبت می‌شود.
10. وضعیت Thread به `pending_operator` تغییر می‌کند.
11. Notification برای اپراتور یا مسئول ارسال می‌شود.
12. Timeline ثبت می‌شود.

### قوانین

- مشتری فقط Threadهای خودش را ببیند.
- مشتری نباید پیام داخلی کاربران سیستم را ببیند.
- مشتری نباید Thread حقوقی داخلی را ببیند، مگر Policy اجازه دهد.
- پیام خالی نباید ارسال شود.
- پیام مشتری باید XSS Safe نمایش داده شود.

---

## پاسخ اپراتور

### مراحل

1. اپراتور وارد Inbox می‌شود.
2. Threadهای مجاز خود را می‌بیند.
3. یک Thread را باز می‌کند.
4. Permission و Scope بررسی می‌شود.
5. اپراتور پاسخ را ثبت می‌کند.
6. پیام ذخیره می‌شود.
7. وضعیت Thread به `pending_customer` یا `resolved` تغییر می‌کند.
8. Notification برای مشتری ارسال می‌شود.
9. Timeline و Log ثبت می‌شود.

### قوانین

- اپراتور فقط Threadهای Scope خودش را ببیند.
- پاسخ اپراتور به مشتری نباید شامل یادداشت داخلی باشد.
- اپراتور نباید اطلاعات مالی حساس داخلی را بدون Permission ببیند.
- ارجاع Thread به اپراتور دیگر باید Audit Log داشته باشد.

---

## پیام‌های داخلی

پیام داخلی فقط برای کاربران داخلی سیستم قابل مشاهده است.

کاربردها:

- یادداشت اپراتور روی مشتری
- توضیح حسابدار درباره پرداخت
- یادداشت حقوقی
- هشدار مدیر
- بررسی داخلی رسید
- هماهنگی درباره پرونده معوقه

قوانین:

- پیام داخلی هرگز به مشتری نمایش داده نشود.
- پیام داخلی باید Badge مشخص داشته باشد.
- مشاهده پیام داخلی نیاز به Permission دارد.
- حذف یا ویرایش پیام داخلی باید Audit Log داشته باشد.
- پیام داخلی می‌تواند به Thread مشتری متصل باشد، ولی visibility آن internal است.

## پیام‌های ربات

Bot Message توسط Eventها ایجاد می‌شود.

### نمونه Eventهای سازنده Bot Message

- `ContractActivated`
- `InstallmentMarkedOverdue`
- `PaymentReceiptUploaded`
- `PaymentReceiptApproved`
- `PaymentReceiptRejected`
- `PaymentApproved`
- `LegalCaseCreated`
- `ContractSettled`
- `IdentityDocumentApproved`
- `IdentityDocumentRejected`

### قوانین

- Bot Message باید template داشته باشد.
- پیام ربات باید فارسی و قابل فهم باشد.
- پیام ربات نباید اطلاعات داخلی حساس نمایش دهد.
- پیام ربات باید به related_type و related_id متصل شود.
- اگر Thread وجود نداشت، طبق Policy ساخته شود.
- ارسال پیام ربات نباید عملیات اصلی را Fail کند؛ خطا باید Log شود.

## اتصال گفتگو به قرارداد یا قسط

هر گفتگو می‌تواند به یک موجودیت مرتبط شود.

نمونه:

```text
related_type = contract
related_id = 125
```

یا:

```text
related_type = installment
related_id = 984
```

قوانین:

- related_id باید معتبر باشد.
- کاربر باید Scope مشاهده موجودیت مرتبط را داشته باشد.
- اگر مشتری مالک قرارداد نیست، نباید Thread مرتبط را ببیند.
- اگر Thread حقوقی است، فقط کاربران حقوقی مجاز آن را ببینند.
- Timeline موجودیت مرتبط باید با پیام‌های مهم بروزرسانی شود.

## ارسال فایل در چت

فایل‌های چت باید توسط Files Domain مدیریت شوند.

### فرمت‌های مجاز پیشنهادی

- jpg
- jpeg
- png
- webp
- pdf

### حداکثر حجم پیش‌فرض

```text
2MB
```

### قوانین

- فایل‌های چت در Private Storage ذخیره شوند.
- مسیر واقعی فایل نباید نمایش داده شود.
- دانلود فایل باید Permission و Scope داشته باشد.
- فایل اجرایی ممنوع است.
- MIME Type و Extension بررسی شود.
- فایل‌های حقوقی یا مالی حساس باید visibility محدود داشته باشند.
- حذف فایل پیوست باید Audit Log داشته باشد.

## خوانده شدن پیام

وقتی گیرنده Thread را باز می‌کند:

1. پیام‌های قابل مشاهده برای او خوانده می‌شوند.
2. وضعیت read برای همان کاربر ثبت می‌شود.
3. unread_count بروزرسانی می‌شود.
4. اگر همه پیام‌ها خوانده شدند، Notification Badge پاک می‌شود.

### قوانین

- خوانده شدن پیام برای هر کاربر جدا ذخیره شود.
- مشتری نباید پیام داخلی را read کند.
- read receipt می‌تواند برای UI استفاده شود.
- خوانده شدن پیام نباید Timeline عمومی بسازد، مگر Settings اجازه دهد.

---

## بستن گفتگو

Thread می‌تواند بسته شود.

### دلایل بستن

- پاسخ کامل داده شده است.
- قرارداد تسویه شده است.
- پرونده بسته شده است.
- پیام اسپم بوده است.
- گفتگو به Thread دیگر منتقل شده است.

### قوانین

- بستن Thread نیاز به Permission دارد.
- مشتری ممکن است بتواند Thread بسته را دوباره باز کند، اگر Settings اجازه دهد.
- بستن Thread داخلی باید Audit Log داشته باشد.
- Thread بسته‌شده نباید پیام جدید داخلی بدون بازگشایی بگیرد، مگر Policy اجازه دهد.

## ارجاع گفتگو

Thread می‌تواند به کاربر یا واحد دیگر ارجاع شود.

نمونه ارجاع‌ها:

- از اپراتور به حسابدار
- از اپراتور به حقوقی
- از حسابدار به مدیر
- از پشتیبانی عمومی به مسئول قرارداد

قوانین:

- ارجاع باید Permission داشته باشد.
- assigned_user_id یا assigned_department_id ثبت شود.
- Notification برای گیرنده ارسال شود.
- Audit Log ثبت شود.
- مشتری فقط پیام ساده ببیند و جزئیات داخلی ارجاع را نبیند.

---

## Validationها

### پیام

- message_body یا attachment الزامی است.
- طول پیام باید در محدوده مجاز باشد.
- HTML خام نباید بدون Sanitization ذخیره یا نمایش داده شود.
- پیام نباید شامل فایل اجرایی باشد.
- وضعیت پیام باید معتبر باشد.

### Thread

- thread_id باید معتبر باشد.
- کاربر باید اجازه مشاهده Thread را داشته باشد.
- related_type باید در لیست مجاز باشد.
- related_id باید وجود داشته باشد.
- Thread archived یا blocked نباید پیام جدید بگیرد، مگر Permission خاص وجود داشته باشد.

### فایل

- فایل باید فرمت مجاز داشته باشد.
- حجم فایل از حد مجاز بیشتر نباشد.
- MIME Type معتبر باشد.
- فایل در Private Storage ذخیره شود.
- دانلود فایل باید Scope Check داشته باشد.

## خطاهای احتمالی

| خطا | رفتار مناسب |
|---|---|
| Thread وجود ندارد | نمایش پیام مناسب |
| Permission کافی نیست | Security Log و عدم دسترسی |
| مشتری مالک Thread نیست | Security Log و عدم دسترسی |
| پیام خالی است | خطا زیر فیلد |
| فایل نامعتبر است | نمایش خطای Upload |

| Thread بسته است | نمایش پیام یا امکان بازگشایی |
| Notification ارسال نشد | ثبت Log و ادامه عملیات |
| Bot Message شکست خورد | ثبت Log بدون Fail کردن عملیات اصلی |

## تست‌های ضروری

### مسیر پیام مشتری

- مشتری وارد پنل شود.
- Thread خودش را باز کند.
- پیام ارسال کند.
- پیام ذخیره شود.
- اپراتور Notification دریافت کند.
- unread_count بروزرسانی شود.

### مسیر پاسخ اپراتور

- اپراتور Thread مجاز را باز کند.
- پاسخ ارسال کند.
- مشتری Notification دریافت کند.
- وضعیت Thread بروزرسانی شود.

### پیام داخلی

- اپراتور پیام داخلی ثبت کند.
- مشتری پیام داخلی را نبیند.
- کاربر داخلی مجاز پیام را ببیند.
- Audit Log ثبت شود.

### Bot Message

- Event قرارداد یا پرداخت رخ دهد.
- Bot Message ساخته شود.
- Thread مرتبط پیدا یا ایجاد شود.
- مشتری پیام مجاز را ببیند.
- خطای Bot Message عملیات اصلی را Fail نکند.

### تست‌های امنیتی

- مشتری نتواند Thread مشتری دیگر را ببیند.
- مشتری نتواند پیام داخلی را ببیند.
- فایل Private از Public قابل دسترسی نباشد.
- فایل اجرایی Upload نشود.
- CSRF نامعتبر رد شود.
- اپراتور خارج از Scope نتواند Thread را باز کند.

## Definition of Done

این Workflow زمانی کامل است که:

- مشتری بتواند پیام ارسال کند و فقط گفتگوهای خودش را ببیند.
- اپراتور بتواند طبق Scope پاسخ دهد.
- پیام داخلی هرگز به مشتری نمایش داده نشود.
- Bot Message براساس Eventهای مهم ساخته شود.
- فایل‌های چت امن و در Private Storage ذخیره شوند.
- پیام‌های مهم به Timeline موجودیت مرتبط متصل شوند.
- Notification پیام جدید ارسال شود.
- شمارنده خوانده‌نشده درست کار کند.
- ارجاع، بستن و بازگشایی گفتگو Audit داشته باشد.
- XSS، CSRF، Permission و Ownership رعایت شود.
- UI چت ساده، سریع، RTL، خوانا و Responsive باشد.
