## هدف Workflow

هدف این Workflow این است که تمام رویدادهای زمانی سیستم، مثل سررسید اقساط، وعده‌های پرداخت، پیگیری‌های اپراتور، اقدامات حقوقی، یادآوری‌های قرارداد، رویدادهای بکاپ و رویدادهای مدیریتی در یک ساختار منظم ثبت، نمایش، یادآوری و پیگیری شوند.

این Workflow باید کمک کند که هیچ سررسید، پیگیری، وعده پرداخت یا اقدام حساس فراموش نشود.

## تعریف Calendar Event

Calendar Event یک رویداد زمان‌دار در سیستم است.

نمونه رویدادها:

- سررسید قسط
- وعده پرداخت مشتری
- پیگیری اپراتور
- جلسه یا اقدام حقوقی
- یادآوری بررسی رسید
- یادآوری بکاپ
- یادآوری تمدید یا بررسی قرارداد
- Reminder داخلی مدیر

هر Calendar Event باید حداقل این اطلاعات را داشته باشد:

- عنوان
- نوع رویداد
- تاریخ و زمان
- وضعیت
- ارتباط با موجودیت اصلی
- مالک یا مسئول
- سطح دسترسی نمایش

---

## تعریف Reminder

Reminder یعنی پیام یا اعلان زمان‌بندی‌شده‌ای که برای یک رویداد ارسال می‌شود.

Reminder می‌تواند از کانال‌های زیر ارسال شود:

- اعلان داخل سیستم
- پیام داخل چت
- پیامک در صورت فعال بودن پلاگین
- ایمیل در صورت فعال بودن
- تلگرام در صورت فعال بودن پلاگین
- اعلان مرورگر در آینده

## مراحل اصلی Workflow

نمای کلی مراحل:

1. یک Domain دیگر نیاز به رویداد زمانی ایجاد می‌کند.
2. Calendar Event ساخته می‌شود.
3. قوانین Reminder از Settings خوانده می‌شود.
4. Reminderهای لازم ساخته می‌شوند.
5. Job زمان‌بندی Reminderها را بررسی می‌کند.
6. در زمان مناسب Notification ارسال می‌شود.
7. Bot Message در صورت نیاز ثبت می‌شود.
8. وضعیت Reminder به `sent` یا `failed` تغییر می‌کند.
9. اگر رویداد انجام شد، وضعیت Event به `completed` تغییر می‌کند.
10. اگر رویداد دیگر لازم نبود، Event یا Reminder لغو می‌شود.
11. Timeline و Log ثبت می‌شود.

## ایجاد رویداد برای اقساط

وقتی اقساط قرارداد تولید می‌شوند، برای هر قسط باید رویداد سررسید ساخته شود.

### مراحل

1. Contract Creation Workflow اقساط را تولید می‌کند.
2. برای هر installment یک Calendar Event ساخته می‌شود.
3. نوع Event برابر `installment_due` می‌شود.
4. starts_at برابر تاریخ سررسید قسط می‌شود.
5. related_type برابر `installment` ثبت می‌شود.
6. related_id برابر installment_id ثبت می‌شود.
7. Reminderهای قبل از سررسید ساخته می‌شوند.
8. Event `CalendarEventsCreatedForInstallments` Dispatch می‌شود.

### قوانین

- برای هر قسط فقط یک Event فعال از نوع `installment_due` ساخته شود.
- اگر تاریخ سررسید تغییر کرد، Event مرتبط هم بروزرسانی شود.
- اگر قسط paid شد، Reminderهای آینده لغو شوند.
- اگر قرارداد cancelled شد، Eventهای اقساط لغو شوند.

## یادآوری قبل از سررسید قسط

سیستم باید طبق Settings قبل از سررسید به مشتری یادآوری کند.

### تنظیمات پیشنهادی

| کلید | توضیح |
|---|---|
| `reminders.installment_before_due_days` | چند روز قبل از سررسید |
| `reminders.installment_due_day_enabled` | یادآوری در روز سررسید |
| `reminders.customer_channels` | کانال‌های ارسال برای مشتری |
| `reminders.operator_copy_enabled` | ارسال کپی به اپراتور |

### مثال

اگر تنظیم شده باشد:

```text
3 روز قبل از سررسید
1 روز قبل از سررسید
روز سررسید
```

برای هر قسط سه Reminder ساخته می‌شود.

---

## یادآوری بعد از معوق شدن قسط

وقتی قسط معوق می‌شود، Reminderهای معوقه ساخته می‌شوند.

### مراحل

1. Overdue Workflow قسط را overdue می‌کند.
2. Calendar Event از نوع `installment_overdue` ساخته یا بروزرسانی می‌شود.
3. Reminder برای مشتری ساخته می‌شود.
4. Reminder برای اپراتور مسئول ساخته می‌شود.
5. در صورت تکرار تأخیر، Reminderهای پیگیری ساخته می‌شوند.
6. اگر پرداخت انجام شد، Reminderهای آینده لغو می‌شوند.

### قوانین

- Reminder معوقه نباید باعث اسپم شود.
- تعداد ارسال در روز باید محدود باشد.
- مشتری نباید پیام‌های داخلی دریافت کند.
- اپراتور فقط Reminderهای Scope خودش را ببیند.

---

## ثبت وعده پرداخت

وقتی اپراتور برای مشتری وعده پرداخت ثبت می‌کند، Calendar Event ساخته می‌شود.

### مراحل

1. اپراتور در Overdue Workflow نتیجه پیگیری را ثبت می‌کند.
2. اگر نتیجه شامل وعده پرداخت بود، تاریخ وعده دریافت می‌شود.
3. Calendar Event از نوع `payment_promise` ساخته می‌شود.
4. Reminder برای اپراتور ساخته می‌شود.
5. Reminder برای مشتری در صورت فعال بودن ساخته می‌شود.
6. اگر پرداخت تا تاریخ وعده ثبت شد، Event completed می‌شود.
7. اگر پرداخت ثبت نشد، Event missed یا failed می‌شود.

### قوانین

- وعده پرداخت، پرداخت واقعی نیست.
- وعده پرداخت نباید وضعیت قسط را paid کند.
- اگر وعده شکست خورد، باید در Timeline و گزارش عملکرد ثبت شود.
- وعده پرداخت نباید بدون تاریخ معتبر ثبت شود.

## یادآوری پیگیری اپراتور

اپراتور می‌تواند برای خودش یا توسط مدیر Reminder پیگیری داشته باشد.

### نمونه کاربردها

- تماس مجدد با مشتری
- بررسی رسید مشتری
- پیگیری ضامن
- پیگیری پرونده حقوقی
- بررسی پرداخت وعده داده‌شده
- تماس بعد از رد رسید

### قوانین

- اپراتور فقط Reminderهای مجاز خودش را ببیند.
- مدیر بتواند Reminder تیم را ببیند.
- Reminderهای انجام‌شده باید completed شوند.
- Reminderهای منقضی‌شده باید missed یا expired شوند.
- Reminderهای مربوط به قرارداد completed باید لغو شوند.

## Validationها

### Calendar Event

- event_type الزامی است.
- title الزامی است.
- starts_at معتبر باشد.
- related_type و related_id اگر وجود دارند باید معتبر باشند.
- assigned_user_id در صورت وجود باید کاربر معتبر باشد.
- visibility معتبر باشد.
- status معتبر باشد.

### Reminder

- calendar_event_id معتبر باشد.
- remind_at معتبر باشد.
- remind_at نباید برای رویداد لغوشده فعال بماند.
- recipient معتبر باشد.
- channel فعال باشد.
- message_template معتبر باشد.
- Reminder تکراری نباشد.

### Permission

- مشتری فقط رویدادهای خودش را ببیند.
- اپراتور فقط رویدادهای Scope خودش را ببیند.
- وکیل فقط رویدادهای حقوقی مجاز را ببیند.
- رویداد سیستمی فقط برای مدیران مجاز نمایش داده شود.

## Timeline

- ایجاد رویداد سررسید قسط
- ارسال یادآوری سررسید
- معوق شدن قسط
- ارسال یادآوری معوقه
- ثبت وعده پرداخت
- ارسال یادآوری وعده پرداخت
- انجام یا شکست وعده پرداخت
- ایجاد رویداد حقوقی
- تکمیل رویداد حقوقی
- لغو Reminderهای آینده بعد از تسویه

Timeline مشتری باید ساده باشد.  
Timeline داخلی می‌تواند جزئیات بیشتری داشته باشد.

## Logging و Audit

### Log عادی

موارد زیر Log عادی دارند:

- ایجاد Event
- ایجاد Reminder
- اجرای Job Reminder
- ارسال Notification
- شکست ارسال Reminder
- تکمیل Event
- لغو Reminder

---

### Audit Log

موارد زیر Audit Log دارند:

- تغییر دستی تاریخ سررسید قسط
- تغییر دستی Reminder حساس
- حذف Event حقوقی
- تغییر مسئول Event
- لغو Reminderهای مهم
- تغییر تنظیمات Reminder
- ایجاد Event حقوقی توسط کاربر داخلی

---

### Security Log

موارد زیر Security Log دارند:

- تلاش مشاهده تقویم کاربر دیگر
- تلاش مشاهده رویداد حقوقی بدون Permission
- تلاش تغییر Reminder بدون Permission
- تلاش دسترسی مشتری به رویداد داخلی
- CSRF نامعتبر
- دستکاری related_id در فرم رویداد

---

## خطاهای احتمالی

| خطا | رفتار مناسب |
|---|---|
| تاریخ رویداد نامعتبر است | نمایش خطا زیر فیلد |
| Reminder تکراری است | جلوگیری از ایجاد تکراری |
| کانال Notification غیرفعال است | ثبت Log و استفاده از کانال جایگزین |
| کاربر مسئول وجود ندارد | نمایش خطا یا تخصیص به مدیر |
| ارسال Reminder شکست خورد | status failed و Retry در صورت تنظیم |
| Event مرتبط حذف شده | Reminder skipped یا cancelled شود |
| قرارداد completed شده | Reminderهای آینده لغو شوند |
| Permission کافی نیست | Security Log و عدم دسترسی |

## تست‌های ضروری

### ایجاد رویداد اقساط

- قرارداد ساخته شود.
- اقساط تولید شوند.
- برای هر قسط Event ساخته شود.
- Reminderهای قبل از سررسید ساخته شوند.
- Event تکراری ایجاد نشود.

### ارسال Reminder

- Job Reminder اجرا شود.
- Reminderهای due ارسال شوند.
- status به sent تغییر کند.
- Notification و Bot Message ثبت شود.
- Reminder تکراری ارسال نشود.

### پرداخت قسط

- قسط paid شود.
- Reminderهای آینده لغو شوند.
- Event سررسید completed شود.
- Timeline ثبت شود.

### وعده پرداخت

- اپراتور وعده پرداخت ثبت کند.
- Event و Reminder ساخته شود.
- اگر پرداخت انجام شد، Event completed شود.
- اگر پرداخت انجام نشد، Event missed شود.

### تست‌های امنیتی

- مشتری نتواند تقویم مشتری دیگر را ببیند.
- اپراتور نتواند Event خارج از Scope را تغییر دهد.
- کاربر بدون Permission نتواند Event حقوقی ببیند.
- CSRF نامعتبر رد شود.

## Definition of Done

این Workflow زمانی کامل است که:

- برای اقساط، رویداد سررسید ساخته شود.
- Reminderهای قبل و بعد از سررسید طبق Settings ساخته و ارسال شوند.
- وعده پرداخت و پیگیری اپراتور در Calendar ثبت شود.
- پرداخت یا تسویه، Reminderهای آینده را لغو کند.
- رویدادهای حقوقی فقط برای کاربران مجاز قابل مشاهده باشند.
- Reminderهای تکراری ساخته یا ارسال نشوند.
- Job ارسال Reminder قابل اطمینان و قابل Log باشد.
- Notification، Bot Message، Timeline، Log و Audit ثبت شوند.
- مشتری فقط رویدادها و یادآوری‌های خودش را ببیند.
- UI تقویم و Reminderها RTL، ساده، سریع و Responsive باشد.
