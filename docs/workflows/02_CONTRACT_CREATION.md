## هدف Workflow

هدف این Workflow این است که کاربر داخلی بتواند برای یک مشتری، قرارداد فروش اقساطی ایجاد کند، کالا یا کالاها را ثبت کند، شرایط مالی را مشخص کند، ضمانت‌ها و ضامن را ثبت کند، اقساط را تولید کند و در نهایت قرارداد را فعال و قابل پیگیری کند.

این Workflow یکی از اصلی‌ترین جریان‌های سیستم است و باید با دقت بالا، Transaction، Validation، Log و Audit پیاده‌سازی شود.

---

## بازیگران

| بازیگر | نقش |
|---|---|
| Admin | ثبت و مدیریت قرارداد |
| Operator | ثبت قرارداد در صورت داشتن Permission |
| Accountant | مشاهده یا بررسی مالی در صورت Permission |
| Customer | مشاهده قرارداد خودش |
| System | تولید شماره قرارداد، اقساط، Timeline و Notification |
| Files System | ذخیره PDF قرارداد |
| Financial System | محاسبه مبالغ قرارداد |
| Notification System | ارسال اعلان‌ها |

## پیش‌نیازها

قبل از اجرای این Workflow باید موارد زیر آماده باشند:

- مشتری در سیستم وجود داشته باشد یا امکان ثبت سریع مشتری فعال باشد.
- قالب قرارداد پیش‌فرض در Settings مشخص شده باشد.
- تنظیمات مالی و اقساط مشخص باشند.
- Permission ایجاد قرارداد تعریف شده باشد.
- Permission مشاهده اطلاعات مالی داخلی مشخص باشد.
- Private Storage برای فایل قرارداد فعال باشد.
- شماره‌گذاری قرارداد فعال باشد.
- CSRF فعال باشد.
- Date Picker استاندارد آماده باشد.

## وضعیت‌های قرارداد در این Workflow

وضعیت‌های اصلی:

| وضعیت | توضیح |
|---|---|
| `draft` | پیش‌نویس |
| `pending_review` | در انتظار بررسی |

## مراحل اصلی Workflow

نمای کلی مراحل:

1. کاربر داخلی وارد صفحه ایجاد قرارداد می‌شود.
2. مشتری انتخاب یا ثبت می‌شود.
3. اطلاعات کالا ثبت می‌شود.
4. شرایط مالی قرارداد ثبت می‌شود.
5. اطلاعات ضمانت ثبت می‌شود.
6. اطلاعات ضامن در صورت نیاز ثبت می‌شود.
7. محاسبات مالی انجام می‌شود.
8. اقساط تولید می‌شوند.
9. قرارداد ذخیره می‌شود.
10. PDF قرارداد تولید می‌شود.
11. رویدادهای تقویم ساخته می‌شوند.
12. Notification و Bot Message ارسال می‌شود.
13. Timeline و Log ثبت می‌شود.
14. قرارداد فعال می‌شود.

## انتخاب یا ثبت مشتری

### مراحل

1. کاربر داخلی مشتری را جستجو می‌کند.
2. سیستم فقط مشتریان مجاز را نمایش می‌دهد.
3. اگر مشتری وجود نداشت، ثبت سریع مشتری انجام می‌شود.
4. اطلاعات پایه مشتری اعتبارسنجی می‌شود.
5. وضعیت احراز هویت مشتری نمایش داده می‌شود.
6. هشدارهای مشتری مثل معوقات یا پرونده حقوقی نمایش داده می‌شود.
7. مشتری برای قرارداد انتخاب می‌شود.

### قوانین

- قرارداد باید به مشتری معتبر متصل باشد.
- اگر مشتری مسدود باشد، ایجاد قرارداد ممنوع یا نیازمند Permission خاص است.
- وضعیت تیک آبی مشتری فقط اطلاع‌رسانی است و جایگزین بررسی انسانی نیست.
- مشتری نباید قرارداد مشتری دیگر را ببیند.

## ثبت اطلاعات کالا

هر قرارداد باید حداقل یک کالا داشته باشد.

### اطلاعات کالا

- نام کالا
- برند
- مدل
- حافظه
- رم
- رنگ
- گارانتی
- IMEI 1
- IMEI 2 در صورت وجود
- قیمت کالا
- توضیحات

### قوانین

- IMEI 1 برای گوشی الزامی است.
- IMEI نباید در قرارداد فعال دیگری تکراری باشد، مگر با Permission خاص.
- اگر چند کالا در قرارداد مجاز باشد، هر کالا باید جداگانه ثبت شود.
- اطلاعات کالا باید در زمان قرارداد Snapshot شود.
- تغییر اطلاعات کالا بعد از فعال شدن قرارداد باید Audit Log داشته باشد.

---

## ثبت شرایط مالی قرارداد

شرایط مالی باید از طریق Financial Calculations Domain بررسی شود.

### اطلاعات مالی

- مبلغ فروش اقساطی
- پیش‌پرداخت
- مبلغ قابل تقسیط
- تعداد اقساط
- مبلغ هر قسط
- تاریخ شروع اقساط
- توضیحات مالی

### قوانین

- مبلغ نهایی قرارداد باید مثبت باشد.
- پیش‌پرداخت نباید از مبلغ قرارداد بیشتر باشد.
- مبلغ قابل تقسیط نباید منفی شود.
- تعداد اقساط باید معتبر باشد.
- مبلغ اقساط نباید از Frontend به عنوان منبع حقیقت پذیرفته شود.
- مشتری نباید فرمول داخلی سود را ببیند.
- متن قرارداد باید از عبارت‌های حقوقی مناسب استفاده کند، مثل «قیمت فروش اقساطی».

## ثبت ضمانت‌ها

ضمانت می‌تواند شامل موارد زیر باشد:

- چک
- سفته
- ضمانت ترکیبی
- سایر ضمانت‌ها

### اطلاعات ضمانت

- نوع ضمانت
- مبلغ ضمانت
- شماره چک یا سفته
- تاریخ چک در صورت وجود
- بانک در صورت وجود
- صاحب ضمانت
- توضیحات
- فایل تصویر ضمانت در صورت نیاز

### قوانین

- ضمانت باید به قرارداد متصل باشد.
- مبلغ ضمانت باید معتبر باشد.
- فایل ضمانت در صورت آپلود باید Private Storage باشد.
- حذف یا تغییر ضمانت قرارداد فعال باید Audit Log داشته باشد.
- اطلاعات ضمانت برای مشتری دیگر قابل مشاهده نیست.

## ثبت ضامن

اگر قرارداد نیاز به ضامن داشته باشد، اطلاعات ضامن ثبت می‌شود.

### اطلاعات ضامن

- نام و نام خانوادگی
- شماره موبایل
- کد ملی
- نسبت با مشتری
- آدرس
- توضیحات
- فایل مدرک در صورت نیاز

### قوانین

- ضامن باید فقط برای قراردادهای مجاز نمایش داده شود.
- اطلاعات ضامن حساس است.
- مشتری نباید اطلاعات ضامن قرارداد دیگر را ببیند.
- تغییر اطلاعات ضامن بعد از فعال شدن قرارداد باید Audit Log داشته باشد.

---

## تولید اقساط

بعد از تأیید اطلاعات مالی، اقساط تولید می‌شوند.

### مراحل

1. مبلغ قابل تقسیط از Financial Calculations گرفته می‌شود.
2. تعداد اقساط بررسی می‌شود.
3. تاریخ اولین قسط بررسی می‌شود.
4. مبلغ هر قسط محاسبه می‌شود.
5. اختلاف گرد کردن روی آخرین قسط اعمال می‌شود.
6. اقساط در جدول installments ساخته می‌شوند.
7. هر قسط به مشتری و قرارداد متصل می‌شود.
8. رویداد Calendar برای سررسید هر قسط ساخته می‌شود.
9. Event تولید اقساط Dispatch می‌شود.

### قوانین

- اقساط نباید دوبار برای یک قرارداد تولید شوند.
- تولید اقساط باید داخل Transaction انجام شود.
- اگر تولید اقساط شکست خورد، قرارداد نباید active شود.
- تغییر اقساط بعد از فعال شدن قرارداد باید محدود و Audit شود.

---

## تولید فایل قرارداد

بعد از ثبت قرارداد، PDF قرارداد باید تولید شود.

### مراحل

1. قالب قرارداد از Settings خوانده می‌شود.
2. متغیرهای قرارداد جایگزین می‌شوند.
3. اطلاعات مشتری، کالا، ضمانت و اقساط وارد قالب می‌شود.
4. PDF یا خروجی چاپی تولید می‌شود.
5. فایل در Private Storage ذخیره می‌شود.
6. Metadata فایل در Files Domain ثبت می‌شود.
7. فایل به contract_documents متصل می‌شود.

### قوانین

- PDF قرارداد باید RTL باشد.
- قالب قرارداد نباید فرمول داخلی سود را افشا کند.
- مشتری فقط قرارداد خودش را ببیند.
- لینک مستقیم Public برای PDF قرارداد ممنوع است.
- اگر PDF تولید نشد، وضعیت قرارداد باید مشخص بماند و خطا Log شود.

---

## فعال‌سازی قرارداد

قرارداد زمانی فعال می‌شود که:

- مشتری معتبر باشد.
- حداقل یک کالا ثبت شده باشد.
- شرایط مالی معتبر باشد.
- ضمانت‌های لازم ثبت شده باشند.
- اقساط تولید شده باشند.
- PDF قرارداد ساخته شده باشد یا Policy اجازه فعال‌سازی بدون PDF بدهد.
- Transaction موفق باشد.

بعد از فعال‌سازی:

- وضعیت قرارداد `active` می‌شود.
- Notification برای مشتری ارسال می‌شود.
- Bot Message در چت مشتری ثبت می‌شود.
- Timeline قرارداد ثبت می‌شود.
- گزارش‌ها داده جدید را نمایش می‌دهند.

---

## Validationها

### مشتری

- customer_id الزامی است.
- مشتری باید وجود داشته باشد.
- مشتری نباید deleted باشد.
- مشتری نباید blocked باشد، مگر Permission خاص وجود داشته باشد.

### کالا

- حداقل یک کالا الزامی است.
- نام کالا الزامی است.
- IMEI برای گوشی الزامی است.
- IMEI نباید تکراری باشد.
- قیمت کالا باید عدد مثبت باشد.

### مالی

- مبلغ قرارداد الزامی و مثبت است.
- پیش‌پرداخت نمی‌تواند منفی باشد.
- پیش‌پرداخت نمی‌تواند از مبلغ قرارداد بیشتر باشد.
- تعداد اقساط باید عدد معتبر باشد.
- تاریخ اولین قسط معتبر باشد.
- مبلغ قابل تقسیط نباید منفی باشد.

### ضمانت

- نوع ضمانت باید معتبر باشد.
- مبلغ ضمانت باید عدد معتبر باشد.
- شماره چک یا سفته در صورت نیاز الزامی است.
- فایل ضمانت باید فرمت مجاز داشته باشد.

### ضامن

- اگر ضامن الزامی است، اطلاعات پایه ضامن باید کامل باشد.
- شماره موبایل ضامن باید معتبر باشد.
- کد ملی ضامن در صورت ثبت باید معتبر باشد.

## Logging و Audit

### Log عادی

موارد زیر Log عادی دارند:

- شروع ایجاد قرارداد
- ثبت آیتم قرارداد
- تولید اقساط
- تولید PDF
- ارسال Notification

### Audit Log

موارد زیر Audit Log دارند:

- ایجاد قرارداد فعال
- تغییر مبلغ قرارداد
- تغییر اطلاعات کالا بعد از فعال‌سازی
- تغییر ضمانت
- تغییر ضامن
- حذف قرارداد
- لغو قرارداد
- فعال‌سازی دستی قرارداد

### Financial Log

موارد زیر Financial Log دارند:

- ثبت مبلغ قرارداد
- ثبت پیش‌پرداخت
- تولید اقساط
- اصلاح شرایط مالی
- تغییر مبلغ قسط

### Security Log

موارد زیر Security Log دارند:

- تلاش ایجاد قرارداد بدون Permission
- تلاش ثبت قرارداد برای مشتری خارج از Scope
- تلاش مشاهده قرارداد مشتری دیگر
- CSRF نامعتبر
- ارسال مبلغ دستکاری‌شده از Frontend

## خطاهای احتمالی

| خطا | رفتار مناسب |
|---|---|
| مشتری معتبر نیست | توقف عملیات و نمایش خطا |
| IMEI تکراری است | نمایش خطا زیر فیلد |
| مبلغ مالی نامعتبر است | نمایش خطای مالی |
| تولید اقساط شکست خورد | Rollback قرارداد |
| تولید PDF شکست خورد | ثبت خطا و وضعیت مشخص |
| فایل ضمانت نامعتبر است | رد فایل و نمایش خطا |
| Permission کافی نیست | Security Log و نمایش عدم دسترسی |
| Transaction شکست خورد | Rollback کامل و پیام عمومی |

## تست‌های ضروری

### مسیر موفق

- انتخاب مشتری
- ثبت کالا
- ثبت شرایط مالی
- ثبت ضمانت
- تولید اقساط
- تولید PDF
- فعال شدن قرارداد
- ارسال Notification
- ثبت Timeline و Log

### تست‌های مالی

- پیش‌پرداخت بیشتر از مبلغ قرارداد رد شود.
- تعداد اقساط نامعتبر رد شود.
- مبلغ Frontend دستکاری‌شده پذیرفته نشود.
- اختلاف گرد کردن در آخرین قسط اعمال شود.

### تست‌های امنیتی

- کاربر بدون Permission نتواند قرارداد بسازد.
- مشتری نتواند قرارداد مشتری دیگر را ببیند.
- فایل قرارداد لینک مستقیم Public نداشته باشد.
- CSRF نامعتبر رد شود.

### تست‌های Transaction

- اگر تولید اقساط شکست خورد، قرارداد فعال نشود.
- اگر ذخیره کالا شکست خورد، قرارداد نیمه‌کاره نماند.
- اگر فعال‌سازی شکست خورد، وضعیت قرارداد مشخص بماند.

## Definition of Done

این Workflow زمانی کامل است که:

- کاربر مجاز بتواند قرارداد کامل ایجاد کند.
- قرارداد به مشتری معتبر متصل باشد.
- کالاها، ضمانت و ضامن درست ثبت شوند.
- شرایط مالی از Service مرکزی محاسبه شود.
- اقساط به صورت صحیح و بدون تکرار تولید شوند.
- PDF قرارداد ساخته و در Private Storage ذخیره شود.
- قرارداد بعد از موفقیت کامل active شود.
- در صورت خطا، داده نیمه‌کاره ایجاد نشود.
- مشتری فقط قرارداد خودش را ببیند.
- Notification، Bot Message، Timeline، Financial Log و Audit ثبت شوند.
- UI ایجاد قرارداد مرحله‌ای، RTL، خوانا و Responsive باشد.
