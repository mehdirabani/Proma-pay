# Proma Pay — Development Philosophy

Version: 1.0

Status: Master Specification

Priority: CRITICAL

---

# Introduction

این فایل فلسفه توسعه رسمی پروژه Proma Pay را تعریف می‌کند.

هدف این سند آموزش نحوه فکر کردن Codex در هنگام توسعه پروژه است.

این فایل صرفاً مجموعه‌ای از قوانین نیست؛ بلکه چارچوب تصمیم‌گیری در پروژه را مشخص می‌کند.

هر زمان بین دو راهکار تردید وجود داشت، تصمیم باید بر اساس این سند گرفته شود.

---

# Core Philosophy

هدف پروژه فقط اضافه کردن قابلیت نیست.

هدف ساخت یک محصول پایدار، توسعه‌پذیر و قابل نگهداری برای سال‌های آینده است.

هر Feature باید کیفیت پروژه را افزایش دهد، نه فقط امکانات آن را.

---

# First Principle

قبل از نوشتن حتی یک خط کد، ابتدا فکر کن.

سپس طراحی کن.

در نهایت پیاده‌سازی کن.

هیچ Feature نباید مستقیماً وارد مرحله کدنویسی شود.

---

# Business First

ابتدا مسئله کسب‌وکار را حل کن.

سپس کد بنویس.

اگر مسئله درست درک نشده باشد، بهترین کدنویسی نیز بی‌ارزش خواهد بود.

---

# Simplicity Over Complexity

همیشه ساده‌ترین راهکار صحیح را انتخاب کن.

از ایجاد ساختارهای پیچیده بدون دلیل خودداری کن.

---

# Reuse Before Create

قبل از ایجاد هر کلاس، فایل یا Component جدید بررسی کن:

آیا مشابه آن وجود دارد؟

اگر پاسخ مثبت است:

از همان استفاده کن.

---

# Refactor Before Expand

قبل از اضافه کردن Feature جدید بررسی کن:

آیا کد فعلی نیاز به Refactor دارد؟

اگر بله:

ابتدا Refactor انجام شود.

سپس قابلیت جدید اضافه شود.

---

# Think About Tomorrow

هر Feature باید به گونه‌ای طراحی شود که:

شش ماه بعد نیز قابل توسعه باشد.

---

# Never Break Existing Features

هیچ Feature جدید نباید باعث شکستن قابلیت‌های قبلی شود.

Backward Compatibility تا حد امکان حفظ شود.

---

# Every Feature Has a Cost

هر قابلیت جدید:

کد بیشتر

تست بیشتر

نگهداری بیشتر

مستندات بیشتر

باگ بیشتر

به همراه دارد.

بنابراین فقط قابلیت‌هایی اضافه شوند که ارزش واقعی ایجاد کنند.

---

# Less Code Is Better Code

هدف نوشتن کد بیشتر نیست.

هدف نوشتن کد کمتر، خواناتر و قابل نگهداری‌تر است.

---

# Avoid Clever Code

از کدهای پیچیده‌ای که فقط نویسنده آن‌ها را متوجه می‌شود استفاده نکن.

کد باید برای توسعه‌دهنده بعدی نیز قابل فهم باشد.

---

# One Source of Truth

هر قانون فقط در یک محل تعریف شود.

نمونه:

محاسبه جریمه

↓

PenaltyService

نه در چند فایل مختلف.

---

# Single Responsibility

هر کلاس فقط یک مسئولیت داشته باشد.

هر فایل فقط یک هدف داشته باشد.

---

# Predictability

رفتار سیستم باید قابل پیش‌بینی باشد.

کاربر نباید از نتیجه عملیات غافلگیر شود.

---

# Consistency

همه صفحات باید رفتار یکسانی داشته باشند.

نمونه:

تمام حذف‌ها Confirmation داشته باشند.

تمام فرم‌ها Validation یکسان داشته باشند.

تمام صفحات از Design System استفاده کنند.

---

# Transparency

هیچ عملیات مهمی نباید مخفی انجام شود.

همه عملیات مهم:

Log

Timeline

Notification

داشته باشند.

---

# Defensive Programming

فرض کن تمام ورودی‌ها اشتباه هستند.

فرض کن اینترنت قطع می‌شود.

فرض کن فایل خراب است.

فرض کن کاربر اشتباه می‌کند.

کد باید در برابر تمام این موارد مقاوم باشد.

---

# Fail Gracefully

در صورت خطا:

سیستم نباید از کار بیفتد.

پیام مناسب نمایش داده شود.

Log ثبت شود.

کاربر راه‌حل دریافت کند.

---

# Modular Thinking

هر قابلیت باید تا حد امکان مستقل باشد.

وابستگی بین ماژول‌ها حداقل ممکن باشد.

---

# Domain Driven Thinking

قبل از طراحی UI، ابتدا Domain را طراحی کن.

Business Logic مهم‌تر از ظاهر است.

---

# Performance Awareness

در هر تغییر از خود بپرس:

آیا این Feature باعث افزایش Query می‌شود؟

آیا باعث افزایش Memory می‌شود؟

آیا سرعت را کاهش می‌دهد؟

اگر بله:

راهکار بهتری پیدا کن.

---

# Security First

اگر بین سرعت توسعه و امنیت تضاد وجود داشت:

امنیت انتخاب شود.

---

# UX Matters

اگر انجام کاری برای کاربر سخت است،

احتمالاً طراحی اشتباه است.

---

# Automation

هر کاری که قابل خودکارسازی است،

نباید به صورت دستی انجام شود.

نمونه:

- اعلان‌ها
- ثبت Timeline
- ثبت Calendar
- حذف فایل‌های موقت
- Backup

---

# No Magic Numbers

هیچ عدد ثابتی داخل کد نوشته نشود.

تمام مقادیر قابل تنظیم باید از Settings خوانده شوند.

---

# Configuration Over Hardcoding

هیچ مسیر، رنگ، شماره کارت، درصد، تعداد اقساط یا متن ثابتی داخل کد قرار نگیرد.

همه موارد باید از تنظیمات قابل تغییر باشند.

---

# Clean Exit

هر Feature باید قابلیت حذف یا جایگزینی داشته باشد.

از وابستگی‌های دائمی جلوگیری شود.

---

# Third Party Packages

قبل از نصب هر Package جدید بررسی کن:

آیا با کد فعلی قابل پیاده‌سازی است؟

آیا نگهداری آن در آینده آسان است؟

آیا امنیت مناسبی دارد؟

آیا واقعاً ضروری است؟

اگر پاسخ قطعی وجود ندارد،

Dependency جدید اضافه نشود.

---

# Database Philosophy

قبل از ایجاد جدول جدید:

آیا جدول موجود قابل استفاده است؟

قبل از ایجاد ستون جدید:

آیا ستون مشابه وجود دارد؟

---

# UI Philosophy

زیبایی مهم است.

اما:

سادگی مهم‌تر است.

---

# Documentation Philosophy

اگر قابلیتی مستند نشده است،

در واقع هنوز کامل نشده است.

---

# Testing Philosophy

هر Feature باید طوری نوشته شود که تست کردن آن ساده باشد.

---

# Codex Behaviour

Codex نباید صرفاً درخواست کاربر را اجرا کند.

Codex باید:

تحلیل کند.

پیشنهاد دهد.

بهینه‌سازی کند.

Refactor کند.

خطرها را اعلام کند.

بهترین راهکار را انتخاب کند.

---

# Implementation Rules

قبل از هر توسعه:

□ Business Rule بررسی شود.

□ ساختار پروژه بررسی شود.

□ Component مشابه بررسی شود.

□ Service مشابه بررسی شود.

□ Migration بررسی شود.

□ Performance بررسی شود.

□ Security بررسی شود.

□ Documentation بررسی شود.

---

# Review Checklist

قبل از Merge:

□ آیا این قابلیت واقعاً لازم بود؟

□ آیا ساده‌ترین راه انتخاب شد؟

□ آیا کد تکراری ایجاد نشده؟

□ آیا وابستگی جدید ضروری است؟

□ آیا پروژه خواناتر شده؟

□ آیا تست انجام شده؟

□ آیا مستندات کامل شده‌اند؟

□ آیا تجربه کاربری بهتر شده است؟

---

# Definition of Done

یک Feature فقط زمانی کامل است که:

✔ مسئله کسب‌وکار را حل کند.

✔ معماری پروژه را حفظ کند.

✔ امنیت را کاهش ندهد.

✔ Performance را کاهش ندهد.

✔ کد را پیچیده‌تر نکند.

✔ مستندات به‌روزرسانی شده باشند.

✔ تست شده باشد.

✔ قابلیت توسعه آینده را حفظ کند.

---

# Final Principle

کد موقتی ننویس.

راه‌حل دائمی طراحی کن.

هدف ساخت یک نرم‌افزار نیست.

هدف ساخت یک محصول حرفه‌ای، قابل اعتماد و قابل توسعه است.
