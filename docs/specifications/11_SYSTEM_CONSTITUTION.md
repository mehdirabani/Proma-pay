# Proma Pay — System Constitution

Version: 1.0  
Status: Master Specification  
Priority: CRITICAL

---

# Introduction

این فایل قانون اساسی رفتار کلی سامانه Proma Pay است.

این سند مشخص می‌کند هر عملیات مهم در سیستم باید چه اثرهایی روی سایر بخش‌ها داشته باشد.

هر قابلیت جدید باید مطابق این فایل طراحی شود.

این سند مستقل از ماژول است و روی تمام بخش‌ها اعمال می‌شود.

---

# Core Principle

هیچ عملیات مهمی نباید فقط در همان صفحه اتفاق بیفتد.

هر عملیات مهم باید در صورت نیاز، اثر خود را روی بخش‌های زیر ثبت کند:

- Log
- Timeline
- Notification
- Calendar
- Report
- Audit
- User Interface
- Permission System

---

# Global System Rules

## Rule 1 — Every Sensitive Action Must Be Logged

تمام عملیات حساس باید در سیستم لاگ شوند.

نمونه عملیات حساس:

- ورود کاربر
- خروج کاربر
- ثبت مشتری
- ویرایش مشتری
- حذف مشتری
- ثبت قرارداد
- ویرایش قرارداد
- حذف قرارداد
- ثبت قسط
- ویرایش قسط
- پرداخت قسط
- رد یا تأیید رسید پرداخت
- آپلود مدرک هویتی
- تأیید یا رد مدرک هویتی
- ارجاع به واحد حقوقی
- ثبت مرحله حقوقی
- ثبت هزینه حقوقی
- تغییر تنظیمات
- بکاپ
- بازیابی بکاپ
- بروزرسانی سیستم

---

## Rule 2 — Every Important Action Must Create Timeline

هر عملیات مهم مربوط به مشتری، قرارداد، قسط، پرداخت یا پرونده حقوقی باید در Timeline ثبت شود.

Timeline باید Append Only باشد.

Timeline نباید حذف یا ویرایش شود، مگر توسط مدیر اصلی و با ثبت Audit Log.

---

## Rule 3 — Every Relevant Event Must Create Notification

اگر عملیاتی برای کاربر یا مدیر اهمیت دارد، باید Notification ایجاد شود.

نمونه:

- ثبت قرارداد جدید
- نزدیک شدن سررسید قسط
- معوق شدن قسط
- ارسال رسید کارت‌به‌کارت
- تأیید پرداخت
- رد پرداخت
- تأیید مدرک هویتی
- رد مدرک هویتی
- ارجاع پرونده به حقوقی
- ثبت جلسه دادگاه
- ثبت رویداد تقویم
- بروزرسانی سیستم

---

## Rule 4 — Every Date-Based Action Must Sync With Calendar

هر چیزی که تاریخ دارد باید بررسی شود که آیا باید در تقویم ثبت شود یا خیر.

مواردی که باید وارد تقویم شوند:

- سررسید اقساط
- وعده پرداخت مشتری
- تاریخ پیگیری اپراتور
- تاریخ جلسه دادگاه
- تاریخ اقدام حقوقی
- رویدادهای دستی مدیر
- Reminderهای سامانه

---

## Rule 5 — Every Delete Must Require Confirmation

هیچ چیزی نباید مستقیم حذف شود.

برای حذف هر داده‌ای باید Confirmation Modal نمایش داده شود.

برای موارد حساس، کاربر باید عبارت تأیید را تایپ کند.

نمونه عبارت:

```text
حذف را تایید می‌کنم
```

موارد حساس:

- مشتری
- قرارداد
- قسط
- پرداخت
- مدرک هویتی
- پرونده حقوقی
- فایل حقوقی
- بکاپ
- تنظیمات مهم

---

## Rule 6 — Prefer Soft Delete

تا جای ممکن حذف‌ها باید Soft Delete باشند.

اطلاعات مهم نباید از دیتابیس حذف شوند.

مواردی که باید Soft Delete شوند:

- مشتریان
- کاربران
- قراردادها
- کالاها
- ضامن‌ها
- ضمانت‌ها
- پرونده‌های حقوقی

مواردی که نباید حذف شوند:

- لاگ‌ها
- Timeline
- پرداخت‌ها
- سوابق مالی
- Audit Logs

---

## Rule 7 — All User Actions Must Respect RBAC

تمام عملیات باید سمت سرور Permission بررسی کنند.

مخفی کردن دکمه در UI کافی نیست.

هر Controller، Route و Service باید در صورت نیاز Permission را بررسی کند.

---

## Rule 8 — No Business Logic In Views

View فقط مسئول نمایش است.

هیچ محاسبه، تصمیم مالی، بررسی Permission یا Query نباید داخل View انجام شود.

---

## Rule 9 — All Outputs Must Be Escaped

هر داده‌ای که در View نمایش داده می‌شود باید Escape شود.

داده خام نباید مستقیم داخل HTML نمایش داده شود.

---

## Rule 10 — All Forms Must Be Validated

تمام فرم‌ها باید Validation سمت سرور داشته باشند.

Validation سمت Frontend فقط برای تجربه کاربری است و جایگزین Validation سرور نیست.

---

# System-Wide Behaviour

## Customer Actions

هر اقدام مشتری باید در صورت نیاز موارد زیر را ایجاد کند:

- Notification برای مدیر یا واحد مرتبط
- Timeline برای مشتری یا قرارداد
- Log
- Review Item در صورت نیاز

نمونه:

ارسال رسید پرداخت:

- وضعیت پرداخت = در حال بررسی
- Notification برای مدیریت
- ایجاد آیتم در بخش بررسی رسیدها
- ثبت Timeline
- ثبت Log

---

## Admin Actions

اقدامات مدیر باید همیشه Audit شوند.

نمونه:

تأیید رسید پرداخت:

- وضعیت پرداخت = تأیید شده
- وضعیت قسط = پرداخت شده یا بخشی پرداخت شده
- حذف فایل رسید از سرور
- Notification برای مشتری
- پیام ربات برای مشتری
- Timeline
- Log

---

## Operator Actions

اقدامات اپراتور باید محدود به دسترسی‌های خودش باشد.

اپراتور می‌تواند:

- مشاهده سررسید گذشته
- تماس با مشتری
- ثبت نتیجه پیگیری
- ثبت وعده پرداخت
- ارجاع به حقوقی
- گفتگو با کاربران مجاز

اپراتور نباید:

- کاربران را ببیند
- قرارداد را حذف کند
- پرداخت را تأیید کند
- تنظیمات را تغییر دهد

---

## Lawyer Actions

واحد حقوقی می‌تواند:

- پرونده‌های ارجاع‌شده را ببیند
- پرونده‌های آماده شکایت را ببیند
- پرونده‌های شکایت‌شده را مدیریت کند
- مراحل پرونده را ثبت کند
- هزینه‌های حقوقی را ثبت کند
- جلسات دادگاه را ثبت کند

هر اقدام حقوقی باید:

- Timeline ایجاد کند
- Log ایجاد کند
- در صورت داشتن تاریخ، Calendar Event ایجاد کند
- Notification برای مدیریت ایجاد کند

---

# Notification Rules

Notificationها باید:

- قابل خواندن باشند
- دارای لینک مقصد باشند
- دارای زمان نسبی باشند
- دارای وضعیت read/unread باشند
- در صورت فعال بودن صدا، Sound ایجاد کنند

Notification نباید شامل اطلاعات حساس غیرضروری باشد.

---

# Bot Rules

ربات سیستم فقط برای اطلاع‌رسانی شخصی استفاده می‌شود.

ربات نباید اطلاعات شخصی کاربران را در کانال عمومی منتشر کند.

نمونه پیام‌های ربات:

- پرداخت شما تأیید شد.
- پرداخت شما رد شد.
- مدرک هویتی شما تأیید شد.
- مدرک هویتی شما رد شد.
- پرونده شما به واحد حقوقی ارجاع شد.
- جلسه دادگاه شما ثبت شد.

---

# Public Channel Rules

کانال اطلاع‌رسانی عمومی فقط برای اخبار عمومی سیستم است.

موارد ممنوع در کانال عمومی:

- تأیید یا رد مدارک هویتی شخصی
- تأیید یا رد پرداخت شخصی
- اطلاعات پرونده حقوقی شخصی
- جزئیات قرارداد شخصی
- اطلاعات اقساط شخصی

---

# Calendar Rules

تقویم برای نقش‌های زیر فعال است:

- مدیر
- اپراتور
- واحد حقوقی
- مشتری

هر نقش فقط رویدادهای مجاز خودش را می‌بیند.

مشتری فقط موارد مربوط به خودش را می‌بیند.

---

# Payment State Rules

وضعیت‌های پرداخت باید قابل پیش‌بینی باشند.

پرداخت کارت‌به‌کارت:

```text
در انتظار پرداخت
↓
در حال بررسی
↓
تأیید شده / رد شده
```

اگر رد شود:

```text
در انتظار پرداخت
```

اگر تأیید شود:

```text
پرداخت شده
```

رسید پس از تأیید یا رد از سرور حذف شود.

---

# File Lifecycle Rules

تمام فایل‌ها باید چرخه عمر مشخص داشته باشند.

## Payment Receipt

```text
Upload
↓
Pending Review
↓
Approved / Rejected
↓
Delete File From Server
```

## Chat Image

```text
Upload
↓
Available For Limited Time
↓
Auto Delete After 7 Days
```

## Identity Document

```text
Upload New Document
↓
Pending Review
↓
Approved:
    Delete Old Document
    Keep New Document
Rejected:
    Delete New Document
    Keep Old Document
```

---

# Settings Rules

هیچ مقدار مهمی نباید Hardcode شود.

موارد زیر باید از Settings قابل تغییر باشند:

- نام سامانه
- لوگو
- متن فوتر
- شماره کارت
- نام صاحب کارت
- فعال بودن کارت‌به‌کارت
- فعال بودن درگاه
- نرخ جریمه
- نرخ پاداش
- تعداد اقساط پیش‌فرض
- فرمت شماره قرارداد
- تنظیمات اعلان
- تنظیمات چت
- مدت نگهداری تصاویر چت
- تنظیمات بکاپ
- تنظیمات بروزرسانی

---

# Report Rules

هر عملیاتی که اثر مالی یا حقوقی دارد باید در گزارش‌ها قابل مشاهده باشد.

گزارش‌ها باید بر اساس داده واقعی تولید شوند.

هیچ گزارش نباید داده محاسبه‌شده نادرست یا قدیمی نمایش دهد.

---

# Audit Rules

Audit Log باید شامل موارد زیر باشد:

- کاربر انجام‌دهنده
- نوع عملیات
- موجودیت مرتبط
- مقدار قبلی در صورت نیاز
- مقدار جدید در صورت نیاز
- IP
- User Agent
- تاریخ و زمان

---

# Maintenance Mode Rules

در حالت Maintenance:

- کاربران عادی نباید وارد سامانه شوند.
- مدیر بتواند وضعیت را ببیند.
- عملیات بروزرسانی یا بازیابی قابل انجام باشد.
- پس از پایان عملیات، Maintenance خاموش شود.

---

# Update Rules

هر Update باید:

- قبل از اجرا Backup بگیرد
- update.json معتبر داشته باشد
- Migration امن داشته باشد
- دیتابیس را حذف نکند
- فایل‌های حساس را بدون دلیل overwrite نکند
- در صورت خطا Rollback کند

---

# Backup Rules

Backup باید شامل موارد زیر باشد:

- Database
- Settings
- Uploaded Files
- Contract Templates
- Private Storage Metadata

اگر ZipArchive در دسترس نبود، سیستم باید fallback داشته باشد.

---

# Implementation Rules

Codex قبل از پیاده‌سازی هر Feature باید بررسی کند:

□ آیا عملیات نیاز به Log دارد؟

□ آیا عملیات نیاز به Timeline دارد؟

□ آیا عملیات نیاز به Notification دارد؟

□ آیا عملیات نیاز به Calendar دارد؟

□ آیا عملیات نیاز به Bot Message دارد؟

□ آیا عملیات نیاز به Report Update دارد؟

□ آیا عملیات نیاز به File Lifecycle دارد؟

□ آیا عملیات نیاز به Permission دارد؟

□ آیا عملیات نیاز به Audit دارد؟

□ آیا مقدار قابل تنظیم است یا Hardcode شده؟

---

# Review Checklist

قبل از Merge هر Feature:

□ هیچ Business Logic داخل View نیست.

□ Permission سمت سرور بررسی شده است.

□ تمام فرم‌ها CSRF دارند.

□ تمام فرم‌ها Validation دارند.

□ عملیات حساس Log دارد.

□ عملیات مهم Timeline دارد.

□ Notification در صورت نیاز ایجاد شده است.

□ Calendar در صورت نیاز به‌روزرسانی شده است.

□ فایل‌ها چرخه عمر مشخص دارند.

□ حذف‌ها Confirmation دارند.

□ اطلاعات حساس به مشتری نمایش داده نمی‌شود.

□ هیچ مقدار مهمی Hardcode نشده است.

---

# Definition of Done

یک Feature زمانی کامل است که:

✔ رفتار آن با قوانین این سند سازگار باشد.

✔ Log لازم ثبت شود.

✔ Timeline لازم ثبت شود.

✔ Notification لازم ایجاد شود.

✔ Calendar لازم ایجاد شود.

✔ Permission سمت سرور بررسی شود.

✔ UI مطابق UI Constitution باشد.

✔ امنیت مطابق Security Constitution باشد.

✔ Performance مطابق Performance Constitution باشد.

✔ مستندات مربوطه به‌روزرسانی شده باشد.
