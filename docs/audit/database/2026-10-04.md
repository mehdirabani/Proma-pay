## Database Architecture

- `OBSERVED`: schema canonical نصب تازه ۷۳ جدول دارد. همه‌ی آن‌ها InnoDB و `utf8mb4` هستند؛ هر جدول primary key دارد. در DDL canonical نوع `FLOAT` یا `DOUBLE` پیدا نشد.
- ۵۰ FK در schema canonical تعریف شده است. مبلغ‌های اصلی قرارداد، قسط و پرداخت از `DECIMAL` استفاده می‌کنند؛ `contracts.down_payment_amount` از `BIGINT UNSIGNED` استفاده می‌کند. واحد/قرارداد دقت مبلغ در همه‌ی مسیرهای قدیمی و importها از روی DDL به‌تنهایی قابل اثبات نیست.
- فایل‌های `database/migrations/` شامل ۵۴ migration مرکزی‌اند؛ علاوه بر آن ۲۰ فایل SQL افزونه پیدا شد. این تعدادها درباره‌ی فایل‌های مخزن‌اند، نه اثبات migrationهای اجراشده روی دیتابیس زنده.
- migration updater نام migration و وضعیت اجرا را در جدول `migrations` نگه می‌دارد و چند دستور destructive را در preflight رد می‌کند. با وجود wrapper تراکنش، DDL در MySQL/MariaDB می‌تواند implicit commit داشته باشد؛ آن wrapper rollback کامل تغییر schema را تضمین نمی‌کند. [مستندات MariaDB درباره‌ی implicit commit](https://mariadb.com/docs/server/reference/sql-statements/transactions/sql-statements-that-cause-an-implicit-commit). rollback فایل‌به‌فایل برای migrationهای مرکزی در این ساختار موجود نیست.

### N+1 و Query داخل حلقه

- **مشتریان:** در نسخه‌ی فعلی، queryهای timeline/trend و اطلاعات مکمل batch شده‌اند. benchmark قبلی با ۱٬۱۰۰ SQL در p95 و اجرای فعلی با ۴۵ SQL سازگار با رفع N+1 قبلی است؛ منبع پیش از تغییر در این snapshot موجود نیست، پس نسبت‌دادن دقیق همه‌ی ۱٬۰۵۵ query به یک حلقه `DERIVED` است.
- **قراردادها:** صفحه‌ی index از helperهای batch برای آمار قسط، مخاطب، ضامن، trend، timeline و آیتم‌ها استفاده می‌کند؛ queryهای تک‌قراردادی در مسیر رندر حلقه‌ای مشاهده نشد.
- **ساخت قرارداد:** `Contract::generateInstallments()` برای هر قسط یک `INSERT` دارد؛ ورودی قرارداد تا ۴۸۰ ماه را می‌پذیرد و کل ساخت قرارداد در transaction انجام می‌شود. این مسیر کم‌تکرار اما write-heavy است؛ benchmark آن در دسترس نیست.
- **Import:** `ImportBatch::create()` برای هر سطر یک `INSERT` جدا می‌زند و batch و ردیف‌ها را در transaction مشترک نمی‌نویسد. خطا در میانه می‌تواند batch ناقص باقی بگذارد. سقف اندازه‌ی import و حداکثر payload قابل اتکا از بررسی فعلی روشن نشد؛ batch insert/transaction به‌عنوان کار بعدی نیازمند تست QA است.
- **Payment correction:** حلقه‌ی اصلاح پرداخت چند قفل، ثبت اصلاحیه و به‌روزرسانی state انجام می‌دهد. ترتیب فعلی برای سازگاری مالی حساس است و به‌عنوان N+1 ساده قابل batch کردن نیست.
- **ابطال گروهی قسط:** query شمارش پرداخت در حلقه‌ی کد وجود دارد، اما action `cancel` پیش‌تر رد می‌شود؛ بنابراین این branch در مسیر فعلی قابل‌دسترسی نیست و آن را هزینه‌ی اجرایی فعال محسوب نکردم.
- **سابقه‌ی پرداخت برای کارت‌ها:** `recentForCustomers()` و `recentForContracts()` همه‌ی پرداخت‌های موفقِ مجموعه‌ی visible را می‌خوانند و بعد در PHP به ۳/۸ مورد برای هر مشتری/قرارداد محدود می‌کنند. `DERIVED`: با رشد history، تعداد سطر و حافظه متناسب با کل history بالا می‌رود. top-N در SQL به قابلیت window وابسته است؛ نسخه‌ی production اثبات نشده و کامنت کد سازگاری MySQL 5.7 را هدف می‌گیرد، پس فعلاً تغییر ندادم.

## Schema Problems و Data Integrity

- **نصب تازه — اصلاح شد:** schema canonical شامل `DROP TABLE IF EXISTS` است. پیش‌تر شاخه‌ی نصب فقط نبودن `users` را می‌سنجید؛ وجود جدول دیگری از همین schema می‌توانست هنگام retry نصب حذف شود. اکنون installer فهرست ۷۳ جدول `CREATE`/`DROP`/`ALTER` را از همان schema استخراج می‌کند و اگر هر هدفی در `information_schema.TABLES` موجود باشد، پیش از اجرای DDL متوقف می‌شود.
- `SELECT u.*` در query صفحه‌ی مشتری شامل `password_hash` و فیلدهای ناموردنیاز بود. این query به projection موردنیاز view/export تغییر کرد: id، نام و مشخصات قابل‌نمایش/ویرایش، avatar، status و `created_at`. این تغییر داده یا schema را تغییر نمی‌دهد.
- **گزارش مالی مشتری — نیازمند تعریف business rule:** query `customerSummariesPaginated()` پرداخت را با `payments.installment_id = installments.id` join می‌کند. `Payment::syncDownPayment()` پرداخت موفق پیش‌پرداخت را با `installment_id = NULL` و `payment_type='down_payment'` ثبت می‌کند؛ پس ستون `paid_total` در export آن نوع پرداخت را نمی‌شمارد. رفتار SQL `OBSERVED` است؛ اینکه گزارش باید «وصول اقساط» باشد یا «تمام پرداخت‌های مشتری» `UNKNOWN` است. به‌دلیل اثر مالی، مقدار را خودکار تغییر ندادم و پیش از اصلاح باید تعریف گزارش و fixture مالی تأیید شود.
- ردیف‌های orphan، duplicate، NULL/empty، drift بین `remaining_amount` و پرداخت‌ها، و سازگاری settlement از دیتابیس زنده بررسی نشدند.
- در مسیرهای اصلی، `Payment::record()` برای پرداخت قسط transaction و `SELECT ... FOR UPDATE` روی قسط دارد؛ ساخت قرارداد نیز داخل transaction است. این بررسی، صحت کامل race/deadlock همه‌ی callbackها را ثابت نمی‌کند.
